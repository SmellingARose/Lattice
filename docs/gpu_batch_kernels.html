Motivation: Why Batch Kernels?

AMR divides the computational domain into many small mesh blocks (typically 64+ leaf blocks for a binary black hole simulation). The naive approach launches a separate GPU kernel for every block at every RK stage. With CK45 (5 stages) and 64 blocks, this means 320 kernel launches per timestep — each with GPU launch overhead and a CPU↔GPU synchronization barrier for ghost exchange.

The batch kernel architecture, inspired by AthenaK (Grete et al. 2024), packs all leaf blocks into a single contiguous buffer and processes them with one kernel launch per operation. This reduces kernel launches by 21x and eliminates per-block synchronization overhead.

Before vs After

BEFORE: Per-Block Architecture

Separate Kernel Per Block

  • Each AMR block processed with its own kernel launch
  • CK45: 5 stages × N blocks per stage
  • Ghost exchange between stages requires CPU↔GPU sync
  • Each block's data mapped/unmapped independently
320kernel launches per step (64 blocks)
AFTER: Packed Batch Architecture

One Kernel For All Blocks

  • All leaf blocks packed into one meshblock_pack_t
  • One RHS + one Sommerfeld + one CK45 update per stage

  • Commit 2: device-side ghost exchange (zero CPU sync)

MeshBlockPack Structure

The meshblock_pack_t (defined in src/amr/meshblock_pack.h) holds all data needed to process every leaf block in a single kernel. It contains:

Core Field Buffers

Four contiguous double* arrays, each sized n_fields × n_blocks × npts:

BufferRoleAllocation
dataEvolved fields U (current state)Always
rhsRight-hand-side F (RHS output)Always
scratchCK45: dU register. Classic RK4: backup U0Always
accumClassic RK4 weighted accumulatorClassic RK4 only (NULL for CK45)

Per-Block Metadata (GPU-Mappable)

Flat arrays carrying block-level information, mapped to GPU as read-only:

ArrayLayoutPurpose
origins[n_blocks × 3]Physical (x,y,z) origin of each block
dx_per_block[n_blocks]Grid spacing (varies by refinement level)
on_boundary[n_blocks × 6]Domain boundary flags per face (x-,x+,y-,y+,z-,z+)
levels[n_blocks]Refinement level per block
neighbor_table[n_blocks × 26]Pack-local neighbor index (-1 if absent)

Coarse Buffer Data (Multi-Level AMR)

For blocks at refinement level > 0, additional contiguous storage for coarse-resolution copies used in multi-level ghost exchange:

FieldDescription
coarse_dataPacked coarse_buf fields: [n_refined × n_fields × coarse_npts]
n_refinedCount of blocks at level > 0
refined_map[n_blocks] — maps pack index to coarse_data slot (-1 if level 0)
coarse_neighbor_table[n_refined × 26] — neighbor indices for coarse_buf exchange

Memory Layout

The pack uses field-major, block-minor, point-innermost ordering. All data for one field across all blocks is contiguous, and within each (field, block) slice, x is the innermost (unit-stride) index.

Indexing Macro

#define PACK_IDX(pack, f, b, idx) \
    ((size_t)(f) * (pack)->n_blocks * (pack)->npts \
     + (size_t)(b) * (pack)->npts + (size_t)(idx))

Where f = field index (0..24), b = block index within pack, idx = point index within block (k*Nt*Nt + j*Nt + i).

Within each (field, block) slice: npts = Ntotal^3 doubles +------------------------------------------------+ | k=0,j=0: i=0,1,2,...,Nt-1 (x unit stride) | | k=0,j=1: i=0,1,2,...,Nt-1 | | ... | | k=Nt-1,j=Nt-1: i=0,1,2,...,Nt-1 | +------------------------------------------------+ Ntotal = N + 2*ghost (e.g. 16+8=24 for N_block=16) npts = 24^3 = 13,824 doubles per (field, block) slice Total pack buffer size: 25 fields × n_blocks × 13,824 points × 8 bytes = 25 × 64 × 13,824 × 8 = ~168 MB per buffer (64 blocks, N=16)

Why Field-Major?

The RHS kernel computes all 25 fields for a single grid point in one invocation. With field-major ordering, the per-field pointer array src_ptrs[f] = data + f*n_blocks*npts + b*npts gives each field its own contiguous memory region. The GPU kernel’s collapse(4) over (b, k, j, i) ensures adjacent threads access adjacent points within each field slice — coalesced memory access on GPU.

AthenaK comparison: AthenaK uses (nmb, nvar, nz, ny, nx) with block outermost. Lattice uses field outermost because the OpenMP target loop iterates for (bidx = 0; bidx < n_blocks * npts; bidx++) and we want all fields for one point computed together by a single thread.

Backend Abstraction

The same C physics kernels run on both CPU and GPU. The backend layer provides two tiers of API:

Two-Tier Backend API Tier 1: Legacy Per-Grid (single-grid stepper, test path) backend_compute_rhs(rhs, src, g, p, func) CPU: #pragma omp parallel for collapse(2) func(rhs, src, g, p, i, j, k) GPU: #pragma omp target teams distribute parallel for collapse(3) ccz4_rhs_point(...) Tier 2: Packed Batch (AMR production path) backend_compute_rhs_packed(pack, p) backend_sommerfeld_packed(pack, p) backend_update_ck45_packed(pack, A, B, dt) backend_zero_packed(pack, which) backend_copy_packed(pack, dst, src) backend_accum_add_packed(pack, weight, dt) backend_axpy_packed(pack, alpha, dt) backend_apply_accum_packed(pack) CPU: #pragma omp parallel for (loops over blocks then cells) GPU: #pragma omp target teams distribute parallel for collapse(4) (b, k, j, i)

Map / Unmap Pattern

Data transfer between host and device is explicit and bracketed around the entire timestep:

FunctionCPU BackendGPU Backend
backend_map_pack(pack, p)No-op (data already in host memory)omp target enter data map(to: ...) for all buffers + metadata
backend_unmap_pack(pack)No-opomp target exit data map(from: ...) syncs data/rhs/scratch/accum back
Key insight: On CPU, the map/unmap are no-ops because all data is already in host memory. This means the packed stepper code is identical for CPU and GPU — only the backend implementations differ. Full testing on macOS (CPU only) validates the packed infrastructure before GPU hardware is available.

GPU Kernel Structure

The batched RHS kernel on GPU uses collapse(4) over block, k, j, i to maximize occupancy. Each GPU thread builds its own per-field pointer arrays and stack-local grid_t, then calls the same ccz4_rhs_point that runs on CPU:

// GPU: one kernel launch for all blocks
#pragma omp target teams distribute parallel for collapse(4)
for (int b = 0; b < nb; b++) {
    for (int k = lo; k < hi; k++) {
        for (int j = lo; j < hi; j++) {
            for (int i = lo; i < hi; i++) {
                // Build per-field pointers into pack layout (~400B stack)
                double *rhs_ptrs[NUM_FIELDS];
                const double *src_ptrs[NUM_FIELDS];
                for (int f = 0; f < NUM_FIELDS; f++) {
                    size_t base = (size_t)f * nb * npts + (size_t)b * npts;
                    src_ptrs[f] = data + base;
                    rhs_ptrs[f] = rhs_data + base;
                }

                // Minimal grid_t on stack (~872B)
                grid_t g_local = { .N=N, .ghost=ghost, .Ntotal=Nt,
                                   .dx=dx_arr[b], .npoints=npts };

                // Same RHS function as CPU path (~4KB stack)
                ccz4_rhs_point(rhs_ptrs, src_ptrs, &g_local, p, i, j, k);
            }
        }
    }
}

CK45 Step: Complete Data Flow

One complete CK45 timestep through the packed stepper (ck45_step_mesh_packed in src/numerics/rk4.c):

ck45_step_mesh_packed(mesh, params, dt) 1. Build pack // mesh_build_leaf_pack() Collect leaf block IDs meshblock_pack_create(n_leaves, npts, ids, -1, RK_CK45) meshblock_pack_load(pack, blocks) // copy fields into contiguous buffer meshblock_pack_load_meta(pack, blocks) // origins, dx, boundary flags, levels meshblock_pack_build_neighbors(pack, blocks) // pack-local neighbor table meshblock_pack_load_coarse(pack, blocks) // coarse_buf data (if AMR) 2. Map to GPU // backend_map_pack(pack, p) [GPU] omp target enter data: data, rhs, scratch, metadata, params 3. Zero dU register // backend_zero_packed(pack, PACK_BUF_SCRATCH) 4. Five CK45 stages (s = 0..4): +----------------------------------------------------------+ | a. Ghost exchange | | Commit 1: packed_ghost_exchange_fallback() | | store pack → blocks (CPU) | | mesh_ghost_exchange (5-phase multilevel, CPU) | | load blocks → pack (CPU) | | Commit 2: backend_ghost_exchange_packed() [device] | | | | b. Batched RHS ONE kernel, all blocks | | backend_compute_rhs_packed(pack, p) | | GPU: collapse(4) over (b, k, j, i) | | CPU: outer b loop, collapse(2) over (k, j) | | | | c. Batched Sommerfeld BCs ONE kernel, all blocks | | backend_sommerfeld_packed(pack, p) | | Only touches ghost cells near domain boundaries | | | | d. Fused CK45 update ONE kernel, flat loop | | backend_update_ck45_packed(pack, A[s], B[s], dt) | | dU[i] = A[s]*dU[i] + dt*F[i] | | U[i] += B[s]*dU[i] | +----------------------------------------------------------+ 5. Unmap from GPU // backend_unmap_pack(pack) [GPU] omp target exit data: sync data/rhs/scratch back to host 6. Store to blocks // meshblock_pack_store(pack, blocks) Copy contiguous pack buffer → individual block grids 7. Enforce algebraic constraints // mesh_enforce_algebraic(m) det(gambar) = 1 rescaling tr(Abar) = 0 projection chi > 0, lapse > 0 floors 8. Restrict to parents // mesh_restrict_to_parents(m) Volume-weighted fine → coarse averaging for cross-level ghost data 9. Free pack // meshblock_pack_free(pack)

Classic RK4 Variant

The classic RK4 packed stepper (classic_rk4_step_mesh_packed) follows the same pattern but uses 4 memory blocks (data, rhs, scratch, accum) instead of 3. The 4 stages use backend_accum_add_packed with weights 1/6, 1/3, 1/3, 1/6 and backend_axpy_packed for intermediate state computation.

Ghost Exchange Strategy

Ghost exchange is the primary remaining bottleneck. It requires communication between blocks that may be at different refinement levels, involving a 5-phase multilevel protocol:

COMMIT 1 (Current)

CPU Fallback

  • meshblock_pack_store — unpack to individual block grids
  • mesh_ghost_exchange — existing 5-phase CPU exchange
  • meshblock_pack_load — repack into contiguous buffer

Full memory round-trip each stage. Correct but slow — data copies dominate on GPU path.

COMMIT 2 (Planned)

Device-Side Kernels

  • Phase 1: same-level face/edge/corner copy (GPU kernel)
  • Phase 2: restrict fine → coarse_buf (GPU kernel)
  • Phase 3: fill coarse_buf ghosts (GPU kernel)
  • Phase 3.5: boundary extrapolation on coarse_buf
  • Phase 4: prolongate coarse_buf → fine ghosts

Zero CPU sync during step. Uses pack neighbor_table for device-to-device copies.

Ghost Exchange: Commit 1 Fallback (per stage) [GPU device memory] [CPU host memory] +-------------------+ +-------------------+ | pack->data | --- store ---> | block[b]->fields | | (contiguous) | | (per-block grids) | +-------------------+ +-------------------+ | mesh_ghost_exchange(m) 5-phase multilevel protocol | +-------------------+ +-------------------+ | pack->data | <--- load --- | block[b]->fields | | (updated ghosts) | | (ghosts filled) | +-------------------+ +-------------------+ This costs ~2 full pack-sized memcpy operations per stage (5 stages = 10 copies). Commit 2 eliminates this by using pack->neighbor_table for device-side copies.

GPU Stack Budget

Each GPU thread in the batched RHS kernel allocates significant stack space for derivative tensors, Christoffel symbols, and Ricci tensor locals. The total must fit within the GPU thread stack limit.

ComponentSizeSource
src_ptrs[25] + rhs_ptrs[25]~400 BPer-field pointer arrays into pack layout
grid_t g_local~872 BStack-local grid struct (N, ghost, Ntotal, dx, npoints, field pointers)
ccz4_rhs_point locals~4,096 BDerivative tensors (d1_chi[3], d2_chi[3][3], d1_h[6][3], d2_h[6][3][3], ...), Christoffel symbols (chris[3][3][3], chris_contracted[3]), Ricci tensor (R_dd[3][3]), gauge terms, etc.
Total per thread~5.3 KB
GPU stack limit: Set via GOMP_NVPTX_NATIVE_GPU_THREAD_STACK_SIZE=16384 (16 KB). The default GCC 13 stack is too small for the CCZ4 RHS kernel. Our 5.3 KB usage leaves comfortable headroom below the 16 KB limit. 
# Required environment variable for GPU execution
export GOMP_NVPTX_NATIVE_GPU_THREAD_STACK_SIZE=16384

# Build and run
make BACKEND=gpu CC=gcc-15
./build/lattice --amr --N 16 --steps 100 --puncture 1.0,0,0,0
