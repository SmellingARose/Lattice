1. What is AMR?

In numerical relativity, we solve Einstein's equations on a 3D grid. The grid spacing dx determines accuracy: smaller dx = more accurate, but also more memory and compute. The problem is that black holes need very fine resolution (dx ~ M/50) while the gravitational waves propagate far away where coarse resolution (dx ~ 2M) is fine.

Adaptive Mesh Refinement solves this by using different resolutions in different regions: fine grids where BHs are, coarse grids everywhere else.

Left: uniform grid wastes resolution on empty space and under-resolves BHs. Right: AMR puts fine grids only where needed.

The key idea: each black hole gets its own set of nested, increasingly fine grids. The wave zone and far field use coarse grids. Total memory is much less than a uniform grid at the finest resolution.

2. The Problem We Hit

Our head-on binary test (m=0.5 each, d=10M separation) at N=128, dx=0.5 showed the BHs dissolving into the grid. The lapse relaxed back toward flat spacetime instead of forming trumpets. Why?

Each BH has coordinate radius ~M/4 = 0.125 for m=0.5. At dx=0.5, that's a quarter of one grid cell. The finite differences can't represent gradients that steep. The numerical dissipation (KO) smooths the BH away in a few timesteps.

To resolve a BH, you need at least ~30 grid points across the horizon. For m=0.5 (horizon radius ~0.25M), that means dx ≤ 0.25/30 ≈ 0.008. But with a uniform grid at dx=0.008 and L=64, you'd need N=8000 — 512 billion grid points, ~100 TB of RAM. Impossible.

AMR solves this: dx=0.008 near each BH, dx=2.0 in the wave zone. With 10 refinement levels, the total memory is ~1-10 GB instead of 100 TB.

3. AMR Approaches Compared

Block-Structured (Berger-Oliger)

Proven N=25 GRChombo, CarpetX, BAM

Rectangular boxes at different resolutions, nested inside each other. An algorithm (Berger-Rigoutsos) clusters cells that need refinement into boxes.

  • Proven at N=25 BHs (GRChombo 2025)
  • Large contiguous arrays → good cache & GPU perf
  • Well-understood inter-level interpolation
  • Bounding-box waste: if 2 BHs are near each other, their boxes merge into one big rectangle covering empty space
  • Regridding (rebuilding boxes) costs 5-15% of runtime
  • Rectangles are a poor fit for spherical BH structure

Oct-Tree Block AMR

New but scaling proven AthenaK, GR-Athena++

A tree of cubes: one root splits into 8 children, each child can split again. Each leaf holds a small uniform block (e.g. 16³ cells). Refines exactly where needed.

  • No bounding-box waste — perfect for scattered N-body
  • 80% GPU scaling at 65,536 GPUs (AthenaK on Frontier)
  • Chi-based refinement auto-tracks any number of BHs
  • 16³ blocks map perfectly to GPU warps/wavefronts
  • Tree traversal less cache-friendly than flat arrays
  • More complex neighbor-finding across tree levels
  • Newer approach, less battle-tested for NR specifically

Wavelet Octree (Dendro-GR)

Niche Dendro-GR

Like oct-tree, but uses wavelet coefficients to decide where to refine. Mathematically optimal error-driven refinement.

  • Wavelet error directly measures where refinement is needed
  • 800 GFLOPS on single A100 GPU
  • No tunable parameters for refinement decisions
  • Complex wavelet machinery to implement
  • Small community, less support
  • Wavelet transform overhead on every regrid

Discontinuous Galerkin (SpECTRE)

Binary only SpECTRE (SXS)

Not finite differences — uses high-order polynomials per element. Exponential convergence for smooth solutions. Elements communicate only through boundary fluxes.

  • Exponential convergence (spectral accuracy)
  • Minimal inter-element communication
  • p-refinement: increase polynomial order instead of splitting cells
  • Requires excision (cut out BH interiors) — fails for N-body mergers
  • Uses generalized harmonic formulation, not CCZ4
  • Would require rewriting everything. Only proven for N=2.

AMReX Framework (Library)

Mature framework CarpetX, GRTeclyn, GRaM-X

Not an AMR type but an AMR library. DOE-funded C++17 framework providing block-structured Berger-Oliger AMR with GPU backends (CUDA/HIP/SYCL). You write physics kernels; AMReX handles ghost zones, subcycling, load balancing, and MPI.

  • Production-quality infrastructure: saves months of AMR plumbing
  • Exascale-proven: 67-77% weak scaling on 4096 Frontier nodes (CarpetX)
  • Multi-GPU vendor: CUDA + HIP + SYCL — no platform-specific code
  • CarpetX has 4th-order subcycling via dense output interpolation
  • Active DOE funding, monthly releases, large community
  • C++17 required — our C17 code would need C++ wrappers or rewrite
  • Block-structured only — same bounding-box waste as Berger-Oliger for N-body
  • No OpenMP target — uses CUDA/HIP/SYCL portability layer instead
  • GRTeclyn (GRChombo→AMReX port) still not production-ready after years of work
  • Large dependency (~500k+ lines C++). No longer "no external dependencies"

NR codes on AMReX: CarpetX (Einstein Toolkit driver, production), GRTeclyn (CCZ4 port of GRChombo, in development), GRaM-X & AsterX (GRMHD, published but BBH waveform accuracy undemonstrated).

Fixed Mesh Refinement (FMR)

Insufficient for N-body BAM, old Carpet

Pre-set nested boxes that move with BHs. No dynamic regridding. Simple and predictable.

  • Dead simple to implement
  • No regridding cost, predictable performance
  • Good for well-understood binary setups
  • Can't handle chaotic orbits (must know BH positions in advance)
  • Fails for N>2 — box overlap wastes memory quadratically
  • BAM's 3-body sims hit domain-size limits

For N scattered BHs: block-structured (and AMReX) wastes space on bounding boxes. Oct-tree refines only where needed. FMR degrades to near-uniform. AMReX trades the bounding-box cost for production-quality GPU + MPI infrastructure.

4. How Many Refinement Levels?

Each level doubles the resolution (with standard 2:1 ratio). The number of levels determines the dynamic range — the ratio between coarsest and finest grid spacing.

LevelsDynamic rangeFinest dx (if coarsest=2M)Use caseArgument
4-616× – 64×M/8 – M/32Head-on, basic binary Simple to debug, fast regrid. Not enough for production waveforms.
8-10256× – 1024×M/128 – M/512Binary inspiral, equal-mass N-body Good balance of accuracy and cost. May miss small remnants.
10-121024× – 4096×M/512 – M/2048Production binary, mass ratio ~10:1 What real codes use. Handles unequal mass. Deep hierarchy = complex subcycling.

Each level doubles resolution. The BH sits at the finest level; gravitational waves propagate outward through coarser levels.

5. Block Size

In oct-tree block AMR, each leaf of the tree holds a uniform block of cells. The block size determines the granularity of refinement.

Block sizeForAgainst
8³ Maximum refinement flexibility. Refine exactly where needed. Too much metadata overhead per block. Poor GPU occupancy (only 512 cells).
16³ ★ Sweet spot. Good GPU occupancy (4096 cells). Matches cache lines. What AthenaK uses. Slightly coarser granularity than 8³.
32³ Fewer blocks = less tree overhead. Great GPU kernel size. Over-refines: a 32³ block might only need refinement in one corner, wasting 7/8 of the cells.

6. Refinement Criteria

How does the code decide where to refine? This is critical for N-body — you can't hard-code BH positions.

Gradient of χ (conformal factor)

Refine wherever |∇χ| exceeds a threshold. Since χ → 0 at each puncture, this automatically detects and tracks all BHs without knowing their positions.

  • Puncture-agnostic: works for any N
  • Naturally gives more levels to smaller BHs (steeper gradients)
  • Cheap to compute (one derivative per point)
  • Doesn't adapt to wave features or constraint violations

χ-min (threshold on conformal factor)

Refine wherever χ < threshold. Even simpler than gradient-based.

  • Trivial to implement
  • Automatically tracks all BHs
  • Doesn't distinguish BH sizes — all get same refinement
  • Threshold needs tuning per scenario

Truncation error estimate

Compute the solution at two resolutions; the difference estimates the error. Refine where error is large.

  • Mathematically optimal — refines where the error actually is
  • ~50% more expensive (need shadow hierarchy)
  • Frequent regridding = high overhead
  • GR-Athena++ found it gave only 3rd-order convergence vs 5th for sphere-in-sphere

Sphere-in-sphere (L2)

Refine all blocks within a spherical region around each puncture.

  • Best mesh efficiency in the GR-Athena++ comparison
  • Simple, predictable geometry
  • Needs to know puncture positions (requires a tracker)
  • Not agnostic — harder for large N

7. Refinement Ratio

RatioForAgainst
2:1 ★ Standard. Simple prolongation/restriction. Stable. What everyone uses. Well-understood interpolation. Need more levels to reach same dynamic range (10 levels for 1024×).
4:1 Half as many levels. Less subcycling overhead. Harder interpolation (4th-order across 4:1 boundary is tricky). Larger resolution jumps cause reflection artifacts.

8. Critical Techniques: CAKO, CAHD, SSL

A 2024 paper by Etienne (arXiv:2404.01137) identified three improvements that reduce constraint violations at AMR boundaries by 2-5 orders of magnitude. These are infrastructure-agnostic — pure physics fixes that work with any AMR scheme.

Why these matter

Without these fixes, the dominant source of numerical error in a moving-puncture AMR simulation is not the finite difference truncation error — it's noise generated at AMR refinement boundaries. The gauge dynamics create a sharp superluminal wave that causes "seven-decade jumps" in constraint violation when crossing between refinement levels. These three techniques eliminate that problem.

CAKO — Curvature-Adjusted KO Dissipation

Multiply the Kreiss-Oliger dissipation coefficient by W = e-2φ (the conformal factor). Near punctures, W → 0, so dissipation vanishes — preserving sharp physical features. In the wave zone, full dissipation suppresses numerical noise.

  • Eliminates artificial damping of BH structure
  • Allows εKO = 0.99 for gauge variables (near CFL max) without harming physics
  • Minimal: one extra multiply per dissipation term

CAHD — Coarse-grid Adjusted Hamiltonian Damping

Scale constraint damping (κ1) based on local grid spacing. On coarser AMR levels, increase damping by 2n. This ensures consistent damping strength across all refinement levels.

  • Maintains consistent constraint damping across resolution changes
  • Prevents constraint violation buildup on coarse levels
  • Need to know the local refinement level (trivial with AMR metadata)

SSL — Slow-Start Lapse

At early times, the 1+log gauge condition creates a sharp superluminal gauge wave that propagates outward. When this wave crosses AMR refinement boundaries, it generates massive constraint violations. SSL adds a Gaussian-damped term to the lapse equation that slows down gauge evolution at early times, letting the gauge wave form more gradually.

  • Eliminates the dominant source of AMR boundary noise
  • Only active for the first ~10-20M of evolution, then vanishes
  • Adds one term to the lapse equation, one tunable timescale parameter
Combined effect: 2 orders of magnitude reduction in strong-field constraint violations, 5 orders of magnitude in the wave-extraction zone. Previously obscured l=m=6 gravitational wave modes become visible above the numerical noise floor. Not adopting these from the start would mean fighting a known problem with a known solution.

The bottlenecks for large N:

  • Timestep: dt ∝ dxmin ∝ M/N for N equal-mass BHs. More BHs = tinier timestep.
  • Initial data: N-puncture elliptic solve gets harder with N. Brill-Lindquist is analytic but only for zero momentum.
  • Chaos: N-body GR is chaotic. Small numerical errors → exponentially diverging trajectories.
  • Load balance: N patches of different sizes moving at different speeds = dynamic imbalance.

Why not AMReX?

AMReX would save us months of AMR plumbing (ghost zones, subcycling, load balancing, MPI). But it forces three trade-offs:

  • C++17 dependency — our pure-C17 codebase would need C++ wrappers or partial rewrite. GRTeclyn (the GRChombo→AMReX port) has been underway for years and is still not production-ready.
  • Block-structured only — AMReX provides Berger-Oliger, not oct-tree. For N=10+ scattered BHs, the bounding-box waste is the exact problem we're trying to avoid.
  • No OpenMP target — AMReX uses CUDA/HIP/SYCL. We'd abandon our OpenMP target GPU strategy.

If our goal were N=2 binary only, AMReX (via CarpetX) would be the pragmatic choice. For N=10+ chaotic N-body, oct-tree is the better fit.

This gives us the best path from head-on binary through N=10+ chaotic BHs, using our existing CCZ4 + moving puncture + OpenMP target architecture. The oct-tree maps naturally to GPU dispatch (one kernel per block), and the ∇χ criterion makes the system completely agnostic to the number of BHs.
