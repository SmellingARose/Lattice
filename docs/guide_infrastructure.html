Learning guide. Explains the foundational data structures and abstractions in Lattice: the grid, field layout, memory model, ghost zones, and backend dispatch. Read this before diving into the evolution equations or AMR code.
Source files: src/core/grid.h, src/core/grid.c, src/core/fields.h, src/core/params.h, src/backend/backend.h

1. Overview

Lattice solves Einstein's field equations in the CCZ4 formulation to simulate black hole spacetimes. The infrastructure layer handles a single job: give the physics code a fast, portable way to read and write 25 three-dimensional arrays of doubles. Everything else — the grid, field layout, memory allocation, ghost zones, and CPU/GPU dispatch — exists to support that.

The Simulation Loop

One time step (RK4 integration): rk4_step() // numerics/rk4.c | +-- for each RK sub-stage: | | | +-- backend_compute_rhs() // backend dispatches to CPU or GPU | | | | | +-- for each interior point (i,j,k): | | | | | +-- ccz4_rhs_point() // reads fields[], writes rhs[] | | | | | +-- FD_D1/FD_D2 // 4th-order finite differences | | +-- Christoffels // from metric + derivatives | | +-- Ricci tensor // from Christoffels + 2nd derivs | | +-- CCZ4 RHS // 25 evolution equations | | | +-- apply_dissipation() // 6th-order Kreiss-Oliger | +-- sommerfeld_bc() // radiative boundary conditions | +-- combine: U += dt * c_s * rhs // RK stage update | +-- enforce_algebraic() // det(gambar)=1, tr(Abar)=0

The physics kernel (ccz4_rhs_point) runs once per grid point per RK sub-stage. With N=128 and RK4, that is 128^3 * 4 = ~8.4 million kernel calls per time step. The infrastructure must make each call cheap: no allocation, no branching, just pointer arithmetic and floating-point math.

2. The 3D Grid

The grid_t struct in src/core/grid.h represents a uniform three-dimensional Cartesian grid. The physical domain is a cube of side length L, centered at the origin, divided into N cells per side, with ghost layers of extra cells on each face for finite difference stencils.

Key grid parameters

IDX: flat 3D indexing

Every field is stored as a flat 1D array of npoints doubles. The IDX macro converts (i, j, k) to a linear index, with x as the innermost (unit-stride) dimension:

#define IDX(g, i, j, k)  ((k) * (g)->Ntotal * (g)->Ntotal + (j) * (g)->Ntotal + (i))

The STRIDE macros give the index offset for moving one cell in each direction. Finite difference stencils use these to step through memory without recomputing IDX:

#define STRIDE_X          1                          // x is unit stride
#define STRIDE_Y(g)       ((g)->Ntotal)              // one full row
#define STRIDE_Z(g)       ((g)->Ntotal * (g)->Ntotal) // one full plane

COORD: cell-centered physical coordinates

Grid points are cell-centered: the coordinate of cell i sits at the center of that cell, not at its edge. The domain runs from -L/2 to +L/2:

#define COORD(g, i)  (((i) - (g)->ghost + 0.5) * (g)->dx - (g)->L * 0.5)

For N=64, L=10: cell i=4 (first interior cell) maps to x = (0 + 0.5) * 0.15625 - 5.0 = -4.921875.

Loop ordering: z (outer) to x (inner)

Standard triple loop over interior points: for (int k = ghost; k < ghost + N; k++) // z: outermost for (int j = ghost; j < ghost + N; j++) // y: middle for (int i = ghost; i < ghost + N; i++) // x: innermost (unit stride!) idx = IDX(g, i, j, k); // fields[f][idx], fields[f][idx+1], fields[f][idx+2]... // ^ consecutive x cells are adjacent in memory Why x innermost? When the inner loop increments i, it advances by STRIDE_X = 1. Consecutive iterations read adjacent memory addresses. The CPU prefetcher loads entire cache lines (64 bytes = 8 doubles), so each cache fetch serves 8 consecutive x-loop iterations. If z were innermost, each iteration would jump by Ntotal^2 = 5184 doubles = 41,472 bytes. Every single access would be a cache miss.

3. Memory Layout: SoA vs AoS

Lattice uses Struct-of-Arrays (SoA) layout. Each of the 25 fields gets its own contiguous array of npoints doubles. The alternative, Array-of-Structs (AoS), would interleave all 25 field values at each grid point.

Side-by-side comparison

Array-of-Structs (AoS) — NOT used Memory: [chi_0 h11_0 h12_0 ... B3_0] [chi_1 h11_1 h12_1 ... B3_1] [chi_2 ...] |<--- 25 doubles (pt 0) --->| |<--- 25 doubles (pt 1) --->| Stencil for chi at point i needs: chi at i-2, i-1, i, i+1, i+2 Memory offsets: ...(i-2)*25, (i-1)*25, i*25, (i+1)*25, (i+2)*25... Stride = 25 doubles = 200 bytes between stencil neighbors One cache line (64 bytes) covers < 1 stencil point. Struct-of-Arrays (SoA) — what Lattice uses Memory: [chi_0 chi_1 chi_2 chi_3 chi_4 chi_5 chi_6 chi_7 ...] <-- chi array [h11_0 h11_1 h11_2 h11_3 h11_4 h11_5 h11_6 h11_7 ...] <-- h11 array ...25 separate arrays... Stencil for chi at point i needs: chi at i-2, i-1, i, i+1, i+2 Memory offsets: ...i-2, i-1, i, i+1, i+2... Stride = 1 double = 8 bytes between stencil neighbors One cache line (64 bytes) covers 8 stencil points.

For stencil-heavy PDE solvers, SoA is the clear winner. Every finite difference operation reads consecutive memory addresses in the x-direction, and the prefetcher can serve the entire stencil from one or two cache lines.

Page-aligned contiguous blocks

Rather than allocating 25 separate arrays per group, Lattice allocates one large contiguous block per group, then slices it into per-field pointers:

// One allocation: 25 fields * npoints doubles, page-aligned
g->fields_block = posix_memalign(4096, NUM_FIELDS * npoints * sizeof(double));

// Per-field pointers are offsets into the block
for (int f = 0; f < NUM_FIELDS; f++)
    g->fields[f] = g->fields_block + f * npoints;

Page alignment (4096 bytes) enables zero-copy GPU buffer mapping — the OS can map these pages directly into GPU address space without copying.

Memory budget

MethodBlocksFormulaN=64N=128N=256

Why CK45 saves memory. The Carpenter-Kennedy low-storage RK method needs only 3 working arrays (fields, rhs, scratch) instead of 4. At N=256, this saves 3.4 GB — the difference between fitting in 16 GB (Apple M4) and not.

4. The 25 Evolved Fields

Lattice evolves 25 scalar fields on the grid. These encode the geometry of curved spacetime in the CCZ4 formulation. Here is what each group represents in plain language:

FieldCountPlain English
chi1How much space is stretched or compressed. Near a black hole, chi approaches zero — space is infinitely stretched.
h_ij6The shape of space. A symmetric 3x3 matrix encoding distances in the x, y, z directions and their cross-terms. Flat space: identity matrix.
K1Is space expanding or contracting? The trace of extrinsic curvature. Positive K means space is shrinking; negative means expanding.
A_ij6How space is being sheared. The traceless part of the extrinsic curvature — measures shape change without volume change.
Theta1CCZ4 error tracker. Should be zero in exact solutions. Non-zero values indicate constraint violations that the damping terms will suppress.
Gamma^i3Connection functions encoding how the coordinate grid bends through space. Evolved independently to improve numerical stability.
lapse (alpha)1How fast does time pass here? The lapse is ~1 far from a black hole, and drops toward ~0.3 at the puncture (the "trumpet" shape).
shift (beta^i)3How do coordinates slide? The shift vector moves grid points to prevent them from falling into the black hole (the "moving puncture" trick).
B^i3Auxiliary field for the Gamma-driver shift condition. Damps oscillations in the shift to keep the coordinates smooth.

The field enum

enum {
    FIELD_CHI = 0,                    // 1 scalar
    FIELD_H11, FIELD_H12, FIELD_H13,  // 6 components of symmetric h_ij
    FIELD_H22, FIELD_H23, FIELD_H33,
    FIELD_K,                          // 1 scalar
    FIELD_A11, FIELD_A12, FIELD_A13,  // 6 components of symmetric A_ij
    FIELD_A22, FIELD_A23, FIELD_A33,
    FIELD_THETA,                      // 1 scalar
    FIELD_GAMMA1, FIELD_GAMMA2, FIELD_GAMMA3,  // 3-vector
    FIELD_LAPSE,                      // 1 scalar
    FIELD_SHIFT1, FIELD_SHIFT2, FIELD_SHIFT3,  // 3-vector
    FIELD_B1, FIELD_B2, FIELD_B3,     // 3-vector
    NUM_FIELDS                        // = 25
};
Deep dive: symmetric tensor storage

A symmetric 3x3 matrix has only 6 independent components (the diagonal plus the upper triangle). Both h_ij and A_ij are stored as 6 consecutive field slots. The sym_table maps 2D indices to flat indices:

static const int sym_table[3][3] = {
    {0, 1, 2},   // (0,0)=0  (0,1)=1  (0,2)=2
    {1, 3, 4},   // (1,0)=1  (1,1)=3  (1,2)=4
    {2, 4, 5}    // (2,0)=2  (2,1)=4  (2,2)=5
};
#define SYM_INDEX(i, j) (sym_table[(i)][(j)])

In physics code, you access h_ij component (i,j) via fields[FIELD_H_START + SYM_INDEX(i,j)]. The symmetry SYM_INDEX(i,j) == SYM_INDEX(j,i) is automatic from the table.

In the RHS evaluation, the metric and extrinsic curvature are loaded into local double[3][3] arrays for clarity. This duplicates the 3 off-diagonal values but makes the tensor algebra readable — the compiler optimizes it away.

Deep dive: the append-only invariant

The field enum is append-only: new fields may only be added at the end, before NUM_FIELDS. Existing entries must never be reordered or removed. This invariant exists because:

  • Output files record field indices. Changing the enum breaks backward compatibility with saved data.
  • The GPU backend may pack field pointers into device arrays. Stable indices prevent synchronization bugs.
  • Phase 2 will add 6 Maxwell fields (E_i, B_i) at indices 25–30. All existing Phase 1 code continues to work unchanged because NUM_FIELDS simply increases from 25 to 31.

5. Ghost Zones

Ghost zones are extra cells surrounding the physical (interior) domain. They hold copies of data from neighboring blocks or boundary conditions, so that finite difference stencils at interior edges have valid data to read.

1D slice of the grid

1D view: Ntotal = N + 2*ghost (ghost = 4) index: 0 1 2 3 | 4 5 6 7 ... 67 | 68 69 70 71 |<-- ghost -->| |<------ interior ------>| |<-- ghost -->| g g g g I I I I I g g g g ghost cells = filled by boundary conditions or neighbor exchange interior cells = computed by the physics kernel Cell 4 (first interior) uses stencil reaching left to cell 0: FD_D1: cells 2,3,4,5,6 (4th-order, 5-point) FD_D2: cells 2,3,4,5,6 (4th-order, 5-point) KO: cells 1,2,3,4,5,6,7 (6th-order, 7-point) Cell 67 (last interior) uses stencil reaching right to cell 71: FD_D1: cells 65,66,67,68,69 FD_D2: cells 65,66,67,68,69 KO: cells 64,65,66,67,68,69,70

Stencil widths

OperationOrderPointsReach (cells from center)
FD_D1 (first derivative)4th52 left, 2 right
FD_D2 (second derivative)4th52 left, 2 right
Kreiss-Oliger dissipation6th73 left, 3 right
Advection (upwind)4th63 left, 2 right (or 2,3)
Why ghost width = 4. The widest stencil (KO dissipation + advection) reaches 3 cells from center. With width 4, even the last interior cell's stencil stays within bounds — no special-case boundary code needed. The extra cell of padding provides safety margin for future stencil extensions.

In AMR, this is the "26-neighbor" exchange (6 faces + 12 edges + 8 corners).

6. Backend Abstraction

The backend layer in src/backend/ provides a single entry point for computing the RHS over the entire grid. Physics code never knows whether it is running on CPU threads or GPU teams.

The 3-function interface

// backend.h — the complete backend API
void backend_init(void);                    // setup (no-op for CPU)
void backend_compute_rhs(rhs, src, g, p, func); // dispatch RHS computation
void backend_cleanup(void);                 // teardown (no-op for CPU)

The rhs_point_func_t is a function pointer to the per-point RHS evaluator. The CPU backend calls it through the pointer; the GPU backend calls ccz4_rhs_point directly (GPU offloading cannot use function pointers).

CPU implementation

// backend_cpu.c
void backend_compute_rhs(rhs, src, g, p, func) {
    #pragma omp parallel for collapse(2) schedule(static)
    for (int k = lo; k < hi; k++)
        for (int j = lo; j < hi; j++)
            for (int i = lo; i < hi; i++)
                func(rhs, src, g, p, i, j, k);  // function pointer call
}

GPU implementation

// backend_gpu.c
void backend_compute_rhs(rhs, src, g, p, func) {
    (void)func;  // GPU calls ccz4_rhs_point directly
    #pragma omp target teams distribute parallel for collapse(3)
    for (int k = lo; k < hi; k++)
        for (int j = lo; j < hi; j++)
            for (int i = lo; i < hi; i++)
                ccz4_rhs_point(rhs, src, g, p, i, j, k);
}
Why OpenMP target instead of CUDA or Metal?

The physics kernels are pure C — no platform-specific intrinsics, no shared memory management, no warp-level operations. OpenMP target offloading lets the same source code compile for CPU (threads) and GPU (teams) with only a pragma change. Benefits:

  • Single codebase. No .cu files, no .metal shaders, no HIP translation. One C file compiles for all targets.
  • Vendor-neutral. GCC 15 targets both NVIDIA (nvptx) and AMD (amdgcn) GPUs from the same source.
  • Simpler debugging. Build with BACKEND=cpu and debug with standard tools. The GPU build is the same code with different pragmas.

The tradeoff: OpenMP target offloading generates less optimized GPU code than hand-tuned CUDA. For Lattice, this is acceptable — the CCZ4 kernel is compute-bound (not memory-bound), and the 20-100x speedup over CPU is sufficient for production runs.

GPU limitations and build system

Function pointers: OpenMP target regions cannot use function pointers. The GPU backend hardcodes the call to ccz4_rhs_point. If a second RHS function is needed (e.g., Maxwell), a new backend dispatch function would be added.

Stack size: The CCZ4 kernel declares large local arrays (derivative tensors, Christoffel symbols, Ricci components — ~4 KB per thread). GCC's default GPU stack is too small, requiring GOMP_NVPTX_NATIVE_GPU_THREAD_STACK_SIZE=16384.

FP64 requirement: Numerical relativity requires 64-bit floating point for stability. Consumer GPUs (RTX 4090, etc.) have 1:32 FP64:FP32 ratio, making them impractical. HPC GPUs (V100/A100/H100) have 1:2 ratio.

Build selection: The Makefile compiles either backend_cpu.c or backend_gpu.c based on the BACKEND=cpu|gpu flag. Both produce the same backend_compute_rhs symbol. No runtime dispatch — the backend is chosen at compile time.

8. Summary: Key Design Decisions

#DecisionRationale
1SoA memory layoutStencil operations stride through one field at a time. SoA makes consecutive x-cells adjacent in memory, enabling cache-line prefetching.
2x innermost, z outermostUnit-stride x access gives optimal cache behavior. OpenMP parallelizes over z-planes (collapse(2) for z,y), keeping x sequential for prefetching.
3Ghost width = 4Covers the widest stencil (6th-order KO: reach 3) with one cell of margin. Avoids special-case boundary logic inside the physics kernel.
4Contiguous block allocationOne posix_memalign per group instead of 25 separate mallocs. Enables zero-copy GPU mapping and reduces TLB misses.
5Page alignment (4096B)Required for zero-copy GPU buffer mapping. Also avoids false sharing on cache-line boundaries between fields.
6N padded to multiple of 16Ensures Ntotal aligns to 128-byte boundaries (16 doubles). Optimal for AVX-512 vector loads and GPU warp-width access patterns.
7Append-only field enumStable field indices across code changes and output files. Phase 2 adds fields without breaking Phase 1 code or saved data.
8Compile-time backend selectionNo runtime dispatch overhead. The Makefile links exactly one backend .o file. Physics code sees only backend.h.
9CK45 default (3 blocks, not 4)Saves 25% memory at no accuracy cost. Critical for fitting N=128 simulations in 16 GB (Apple M4).
