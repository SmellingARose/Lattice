1. Background: From Psi4 to h(t)

Gravitational wave detectors measure the strain h(t) = h+ - i hx, the fractional change in arm length. Numerical relativity simulations compute the Weyl scalar Psi4, a curvature invariant. The two are related by a double time integral:

Psi4 = d2h / dt2   ⇒   h(t) = ∫∫ Psi4 dt dt

Equivalently, the Bondi news function N(t) = dh/dt satisfies Psi4 = dN/dt. CCE gives the news N directly at future null infinity; fixed-radius extraction gives Psi4 at finite radius, requiring both integration and extrapolation.

The fundamental problem: Psi4 is only cleanly defined at future null infinity (denoted J+ or "scri+"), where the spacetime is asymptotically flat. At any finite radius r, the measured Psi4 contains:

  • The physical radiation: Falls off as 1/r (the piece we want)
  • Near-field contamination: Coulomb-like terms falling as 1/r2, 1/r3, ... (the piece we don't want)
  • Gauge artifacts: Coordinate-dependent contributions that vanish only at J+

Both extraction methods attempt to isolate the physical radiation. They differ in how.

Spherical Harmonic Decomposition

Both methods decompose the signal into angular modes using spin-weight -2 spherical harmonics:

Psi4(t,r,theta,phi) = ∑l,m Psi4lm(t,r) · -2Ylm(theta,phi)

The dominant mode is (l,m)=(2,2). Subdominant modes (2,1), (3,3), (4,4) matter for parameter estimation. The m=0 modes carry the gravitational wave memory — a permanent displacement that only CCE captures correctly.

2. Method 1: Fixed-Radius Extraction + Extrapolation

How It Works

Cauchy Evolution Grid +-----------------------------------------+ | | | **** **** | | * BH *------* BH * (binary orbit) | | **** **** | | \ / | | \/ GW radiation propagates | | /\ outward through grid | | / \ | | - - -[r=50M]- - - - extraction sphere | | | | - - - - [r=75M] - - - extraction sphere | | | - - - - - [r=100M]- - extraction sphere | | | - - - - - - [r=150M] - extraction sphere | | | - - - - - - - [r=200M] extraction sphere | | +-------[Sommerfeld BC at outer boundary]-+ | v Polynomial extrapolation in 1/r to approximate r -> infinity

Step-by-Step Pipeline

  1. Compute Psi4 on the Cartesian grid. At each timestep, construct the Weyl tensor projection using the evolved CCZ4 fields (metric, extrinsic curvature, Christoffel symbols). This requires first and second spatial derivatives of the metric, plus a null tetrad constructed from the unit radial vector.
  2. Interpolate onto extraction spheres. Place 4-6 coordinate spheres at radii r = {50, 75, 100, 150, 200} M. At each timestep, interpolate Psi4 (real and imaginary parts) from the Cartesian grid onto Ntheta x Nphi angular points on each sphere. Typical: 20 x 40 = 800 points per sphere, using Gauss-Legendre nodes in theta and uniform nodes in phi.
  3. Decompose into (l,m) modes. At each angular point, multiply by conj(-2Ylm) and integrate over the sphere using quadrature weights. Output: the complex time series r*Psi4lm(t) at each extraction radius.
  4. Extrapolate to r -> infinity. For each mode and each time sample, fit the value at multiple radii to a polynomial in 1/r and evaluate at 1/r = 0. Typically use polynomial orders N=2,3,4 and compare for convergence: r · Psi4lm(t,r) = a0(t) + a1(t)/r + a2(t)/r2 + ... The coefficient a0(t) is the extrapolated value at infinity.
  5. Integrate to strain. Convert Psi4lm(t) to strain hlm(t) via Fixed Frequency Integration (FFI): transform to frequency domain, divide by -omega2, apply a low-frequency cutoff f0 to suppress drift, transform back. The cutoff f0 is chosen slightly below the orbital frequency.

Strengths

  • Simple to implement — ~300 lines of C for the in-simulation part, ~200 lines of Python for post-processing
  • Well-tested — every NR code has used this for 15+ years
  • No external dependencies — the entire pipeline is self-contained
  • Fast at runtime — interpolation + quadrature is negligible cost compared to evolution
  • Good enough for most science — produced every waveform in the first LIGO/Virgo catalogs

Limitations

  • Cannot capture gravitational wave memory — the m=0 modes carry a permanent displacement that is suppressed by the extrapolation procedure and by the FFI integration cutoff
  • Residual gauge dependence — Taylor et al. (2013) showed that running the same physics with two different gauge conditions produces the same CCE waveforms but different extrapolated waveforms
  • Polynomial extrapolation can diverge — the 1/r expansion is asymptotic, not convergent. High polynomial orders may oscillate. Typical practice: use N=2 to N=4 and take the spread as an error bar
  • Requires large grids — extraction spheres at r=200M need the grid to extend that far, eating into resolution budget. AMR helps but adds complexity.

3. Method 2: Cauchy-Characteristic Extraction (CCE)

The Core Idea

Instead of extrapolating finite-radius data with a polynomial fit, CCE solves Einstein's equations on null (light-cone) slices from a finite worldtube all the way to future null infinity. The waveform is read off at J+, where it is gauge-invariant by definition.

Cauchy Domain Characteristic Domain (3+1 spacelike slices) (null slices u = const) +-----------------------+ | | | **** **** | Null slices foliate | * BH *---* BH * | from worldtube to | **** **** | future null infinity | \ / | | GW radiation | u=t3 / | / \ | / -----> J+ (scri+) | / \ | u=t2 / | / \ | / -----> J+ +----[worldtube r=R]----+ u=t1 / | ^ | / -----> J+ | | | worldtube | metric data (inner boundary) | stored here v Cauchy code writes CCE code reads worldtube, g_ij, K_ij, alpha, evolves Bondi-Sachs equations beta^i on the worldtube on null slices out to J+

Step-by-Step Pipeline

  1. Choose a worldtube. A coordinate sphere at radius R (typically 50-200 M). During the Cauchy evolution, store the full 3-metric gij, lapse alpha, shift betai, and their time/spatial derivatives on this sphere at every output timestep. Store as spherical harmonic coefficients up to lmax ~ 20.
  2. Transform to Bondi-Sachs gauge. The Cauchy data is in 3+1 coordinates (Cartesian, with 1+log lapse and Gamma-driver shift). The characteristic code needs data in Bondi-Sachs null coordinates. This transformation involves Jacobians, spectral decomposition, and solving a system of ODEs on each angular patch. SpECTRE's PreprocessCceWorldtube handles this automatically.
  3. Evolve the Bondi-Sachs equations. The characteristic evolution solves a hierarchical system of hypersurface equations on each null slice u = const:
    • Start at the worldtube (inner boundary) with known data
    • Integrate outward along null rays toward r -> infinity
    • The equations are a nested sequence of ODEs + angular differential operators
    • The Bondi-Sachs variables: J (shear), U (angular metric), Q (gauge), W (mass aspect), Beta, H, R
  4. Compactify. The radial coordinate is compactified so that J+ is at a finite grid point. SpECTRE uses a spectral method (Chebyshev in the compactified radial coordinate) so the entire domain from R to infinity is resolved with ~30-50 radial points.
  5. Read off the waveform at J+. At the outermost grid point (r = infinity), the Bondi news N and strain h are directly available. No extrapolation needed. No integration of Psi4 needed — the strain is a primary output.

The Bondi-Sachs Formulation

The metric in Bondi-Sachs coordinates takes the form:

ds2 = -(e2Beta V/r - r2 hAB UA UB) du2 - 2 e2Beta du dr - 2 r2 hAB UB du dxA + r2 hAB dxA dxB

where u is retarded time (labels null hypersurfaces), r is the luminosity distance, and xA = (theta, phi) are angular coordinates. The key feature: the Einstein equations on these null slices decompose into a nested hierarchy of equations that can be integrated radially, one variable at a time, given data at the inner boundary. This is fundamentally different from (and cheaper than) the hyperbolic Cauchy evolution.

What SpECTRE's CCE Module Does

SpECTRE CCE (arXiv:2110.08635) State of the art

The SpECTRE CCE module is the current standard implementation. Key features:

  • Standalone mode: Accepts worldtube data from any Cauchy code (not just SpECTRE) via HDF5 files. AthenaK, GR-Athena++, and Einstein Toolkit have all used it.
  • Input formats: Cartesian metric (nodal or modal), ADM variables (with extrinsic curvature), or native Bondi-Sachs. A preprocessing utility handles conversion.
  • Spectral convergence: Uses spectral methods in both radial and angular directions. Free of pure-gauge logarithms that plagued earlier implementations.
  • Outputs: Strain h, news N, all five Weyl scalars (Psi0 through Psi4), all at J+ and decomposed into spherical harmonic modes.
  • Angular resolution: Typically lmax = 20 with filter at l = 18. No improvement above lmax = 24.
  • Speed: Fast enough to be a post-processing step. For a typical BBH simulation, CCE takes minutes to hours (compared to days-weeks for the Cauchy evolution itself).

Strengths

  • Gauge-invariant by construction — the waveform at J+ is physically unambiguous
  • Captures gravitational wave memory — the m=0 modes and the non-oscillatory displacement are correctly extracted
  • No extrapolation error — the waveform is computed at infinity, not fitted there
  • Produces strain directly — no need for FFI integration of Psi4 (avoids integration drift entirely)
  • Standalone module exists — SpECTRE's CCE is freely available and accepts data from external codes

Limitations

  • Worldtube radius sensitivity — CCE waveforms show "stronger dependence on the radius of the CCE worldtube" than extrapolation on extraction radius (Taylor et al. 2013). Must test multiple radii.
  • Data volume — storing full metric + derivatives on the worldtube at every output step generates large files (GBs to tens of GBs for long inspirals)
  • Implementation complexity — writing a CCE code from scratch is a multi-year effort. The Bondi-Sachs equations are intricate (spectral angular operators, compactified radial domain, gauge transformations).
  • Junk radiation — initial data artifacts ("junk radiation") pass through the worldtube and produce spurious oscillations in the CCE output. Must discard the first ~100-200 M of CCE data.
  • C++ dependency — SpECTRE is a large C++ codebase. Using it as a library or standalone tool adds a build dependency.

5. Accuracy Requirements: What Do Detectors Need?

Lindblom Criteria (arXiv:0809.3844)

Lindblom (2009) derived the fundamental accuracy standards for gravitational wave data analysis. A model waveform hmodel must satisfy:

ApplicationMismatch RequirementWhat This Means
DetectionMismatch < 0.03 (3%)Lose <10% of events due to template inaccuracy
Parameter estimation (current LIGO)Mismatch < 1/(2 * SNR2)At SNR=20: mismatch < 1.25 x 10-3
Parameter estimation (design LIGO)Mismatch < 2 x 10-4At SNR=80 (loudest expected events)
LISA / 3G detectorsMismatch < 10-6 to 10-5SNR up to ~1000. Tenfold accuracy increase needed.

Where Does Extraction Error Sit?

The Error Hierarchy
Total waveform error = truncation error + extraction error + modeling error

For current production simulations:

  Truncation error (finite grid spacing):     ~10^-3 to 10^-4  mismatch
  Extraction error (finite radius / method):  ~3 x 10^-4       mismatch
  Modeling error (PN hybridization, etc.):    ~10^-4 to 10^-5  mismatch
                                              ________________
  Combined:                                   ~10^-3           mismatch

For current LIGO (SNR ~20):  requirement is ~10^-3  -->  ADEQUATE
For design LIGO (SNR ~80):   requirement is ~2x10^-4 --> MARGINAL
For LISA / 3G (SNR ~1000):   requirement is ~10^-5  -->  INSUFFICIENT

At current LIGO sensitivity, truncation error and extraction error are comparable. Improving one without the other gives diminishing returns. For 3G detectors and LISA, both must improve by 1-2 orders of magnitude — which is where CCE (or hyperboloidal methods) becomes essential.

6. Hybrid Approaches

In practice, nobody runs only CCE or only extrapolation. The standard workflow is layered:

Development Cycle Production Catalog ======================== ======================== 1. Evolve with Cauchy code 1. Same Cauchy evolution | | v v 2. Quick-look Psi4 at 2. Store worldtube data r=100M (real-time diagnostic) (full metric on sphere) | | v v 3. Extrapolate to infinity 3. Run SpECTRE CCE (minutes of post-processing) (hours of post-processing) | | v v 4. "Is the physics right?" 4. Final strain at J+ (gauge wave test, convergence) (gauge-invariant, with memory) | | v v 5. Iterate on parameters 5. Package for catalog (LIGO HDF5 format)
The AthenaK Model (arXiv:2506.06838) Best current practice

AthenaK's GW150914 simulation demonstrates the modern hybrid workflow:

  • During evolution: output full metric data on a cylindrical worldtube at r = 49-51 M
  • Also extract Psi4 at multiple finite radii for quick comparison
  • Post-simulation: convert worldtube data with scripts, feed to SpECTRE CCE
  • Apply scri package to transform to super rest frame of the binary
  • Result: phase accuracy ~0.12-0.35 rad vs SXS reference (dominated by resolution, not extraction)
  • Amplitude accuracy: 0.2-0.4%

Total CCE pipeline adds negligible cost compared to the Cauchy evolution itself.

Middle Ground: Memory Correction

The SXS catalog applies a memory correction to extrapolated waveforms: compute the expected memory from the energy flux of the (l ≥ 2, m ≠ 0) modes using the Christodoulou formula, then add it to the m=0 modes. This recovers most of the memory signal without running CCE. The scri Python package implements this. It is an approximation — the correction assumes only leading-order memory and misses memory-of-memory effects — but it bridges the gap for catalogs that lack full CCE.

7. Emerging Alternative: Perturbative Hyperboloidal Extraction (PHE)

arXiv:2508.05743 (2025) New approach

A third method is emerging: perturbative hyperboloidal extraction. The idea: use NR data at a finite worldtube as the inner boundary for a perturbative (linearized) time-domain evolution on hyperboloidal slices that reach J+.

  • Solves the Regge-Wheeler-Zerilli equations (linearized Einstein equations for perturbations of Schwarzschild) on hyperboloidal coordinates
  • Much simpler than full Bondi-Sachs evolution — 1D radial equations per (l,m) mode
  • Demonstrated to match CCE waveforms for BBH mergers, gravitational collapse, and neutron star mergers
  • "Can sometimes provide even more robust predictions than CCE, reducing unphysical features"
  • Captures memory effects (hyperboloidal slices reach J+)
  • Implementation: 1D PDE solver per mode — much more tractable than full CCE

Too early to call this production-ready, but it may become the practical middle ground between extrapolation and full CCE in the next 2-3 years.

Path A: Fixed-Radius Extraction (Recommended First)

Implementation Plan Phase 3 priority

Step 1: Psi4 computation (~200 lines of C)

Compute the Newman-Penrose scalar Psi4 = Cabcd na mbarb nc mbard at each grid point. Requires:

  • Physical Riemann tensor from evolved CCZ4 variables
  • Null tetrad (l, n, m, mbar) constructed from the unit radial vector and the spatial metric
  • Second spatial derivatives of the conformal metric (already computed in RHS, but need them independently for diagnostics)

Reference: GRChombo Source/CCZ4/Weyl4.impl.hpp

Step 2: Extraction sphere interpolation (~100 lines of C)

Lattice already has 4th-order Lagrange interpolation at arbitrary (x,y,z) in interpolate.h, including the block-aware AMR variant. The 5-point stencil (125 source points per interpolation) is already implemented and tested. Need to add:

  • Sphere sampling: generate Ntheta x Nphi points at (r sin(theta) cos(phi), r sin(theta) sin(phi), r cos(theta))
  • Gauss-Legendre nodes and weights for theta quadrature
  • Uniform nodes for phi (with trapezoidal rule)

Step 3: Spin-weighted spherical harmonic decomposition (~50 lines of C)

The spin-weight s=-2 spherical harmonics can be computed from the Goldberg formula. For lmax=4, need:

-2Ylm(theta,phi) = (-1)m sqrt((2l+1)/4pi) dl-m,-2(theta) eim*phi

where dlm,s is the Wigner d-matrix. Precompute and store for all angular points.

Step 4: Mode output (~30 lines of C)

Write r*Psi4lm(t) to ASCII files, one per (l,m) mode per extraction radius. Format: t Re(Psi4) Im(Psi4) per line.

Step 5: Post-processing (~200 lines of Python)

  • FFI integration: Psi4lm(t) -> hlm(t) using frequency-domain integration with low-frequency cutoff
  • Extrapolation: fit r*Psi4lm(t,r) vs 1/r at each time step, evaluate at 1/r=0
  • Optional: memory correction via Christodoulou formula

Total estimate: ~500 lines of C + ~200 lines of Python.

Path B: CCE-Ready Worldtube Output

Future Addition After fixed-radius works

To feed SpECTRE CCE, Lattice needs to output worldtube data. SpECTRE accepts several formats; the simplest for Lattice is "metric nodal" (Cartesian metric on collocation points).

What to store on the worldtube:

  • Spatial metric components: gxx, gxy, gxz, gyy, gyz, gzz (recover from chi and hij)
  • Lapse alpha and shift betai
  • Time derivatives of the above (use the RHS values from the evolution)
  • Spatial derivatives (use the finite difference stencils)

Angular sampling: Gauss-Legendre in cos(theta), uniform in phi. lmax = 20 requires ~21 x 40 = 840 points per timestep.

Output format: HDF5 file following SpECTRE's worldtube conventions. Each timestep writes the metric data as spin-weighted spherical harmonic coefficients (or nodal values on the collocation grid).

Storage estimate: For a worldtube at r=100M, outputting every 0.1M in time over 1000M of evolution: ~10,000 time steps x ~20 metric quantities x 840 points x 8 bytes = ~1.3 GB. Manageable.

Implementation effort: ~300 lines of C for the worldtube output + conversion script. Requires HDF5 library (or a custom binary format with a Python converter to HDF5).

Path C: Perturbative Hyperboloidal Extraction (Future)

Long-Term Option Research-stage

If PHE matures, it could be implemented directly in C within Lattice:

  • Solve 1D Regge-Wheeler-Zerilli equations per (l,m) mode on a hyperboloidal grid
  • Inner boundary: Psi4 mode data at the extraction sphere (same as fixed-radius extraction)
  • Outer boundary: J+ is at a finite grid point (compactified coordinate)
  • No external dependencies (pure C, 1D PDE solver)
  • Would capture memory and be gauge-invariant, without the complexity of full CCE

Estimated effort: ~1000 lines of C. But the method is too new (2025) to commit to implementing.

9. Recommendation for Lattice

Two-Phase Strategy

Phase 3a: Fixed-Radius Extraction (implement now)

  1. Implement Psi4 computation at grid points (src/diagnostics/psi4.c)
  2. Interpolate onto 4-6 extraction spheres using existing interpolate.h infrastructure
  3. Decompose into (l,m) modes with spin-weight -2 spherical harmonics
  4. Output r*Psi4lm(t) time series per radius
  5. Python post-processing: FFI integration + polynomial extrapolation

This gives Lattice waveform catalog capability immediately. Sufficient for current LIGO science, debugging, convergence testing, and most publications.

  1. Add worldtube data output: full metric + derivatives on a coordinate sphere
  2. Write conversion script to SpECTRE CCE input format
  3. Validate: compare CCE waveforms with extrapolated waveforms for a test case

This gives Lattice access to gauge-invariant waveforms at J+ for precision science and GW memory studies, using SpECTRE's existing CCE implementation as a post-processing tool. No need to reimplement characteristic evolution.

The Real Bottleneck: Evolution Accuracy, Not Extraction Method

Garbage In, Garbage Out Critical insight

CCE eliminates extraction artifacts, but it cannot fix evolution errors. If the Cauchy data on the worldtube has large truncation error, SpECTRE's CCE will faithfully propagate that error to null infinity. The total waveform error is a chain:

FD truncation error  →  AMR prolongation error  →  interpolation error  →  extraction error
   O(dx^p)               O(dx^q) at boundaries       O(dx^4) on sphere        O(1/r) or 0 (CCE)
     ^                          ^                           ^                        ^
     |                          |                           |                        |
  DOMINATES               can bottleneck              usually small           CCE removes this
  at current              6th-order FD if
  resolutions             prolongation is 4th

For next-generation detectors (LISA, Cosmic Explorer, Einstein Telescope), every link in this chain must be addressed:

The Full Accuracy Chain for Next-Gen Quality

LinkCurrent StateRequired UpgradeWhy
1. FD order4th-order (O(dx4))6th-order (O(dx6))Reduces truncation error by dx2 at every point, including worldtube. Ghost=4 already sufficient.
2. AMR prolongation4th-order Lagrange6th-order Lagrange4th-order prolongation injects O(dx4) error at refinement boundaries, bottlenecking the 6th-order evolution.
3. Wave zone resolutionExtraction at r=50-100M on coarse root levelExtra AMR level in wave zone, or worldtube at r=25M in refined regionRoot-level dx~1-2M gives O(1) truncation error at the extraction sphere. Useless for precision.
4. Extraction methodNot yet implementedWorldtube output + CCE (via SpECTRE)Gauge-invariant strain at J+, GW memory, no finite-radius artifacts.
The AMR insight: With AMR, the extraction sphere at r=50-100M sits on the coarsest grid level. The truncation error at the extraction radius is set by dx_coarse, not dx_fine. This is why CCE with a worldtube at r=20-25M (in the refined region) is superior for AMR codes — it sidesteps the wave zone resolution problem entirely. The characteristic solver propagates the waveform from r=25M to infinity without needing a resolved Cauchy grid in the wave zone.

The Bottom Line

For Current LIGO Science

Fixed-radius extraction with polynomial extrapolation works. Truncation error dominates extraction error at current resolutions. Implement this first for quick diagnostics and debugging.

For Next-Gen Detectors (LISA / 3G)

The full chain is required: 6th-order FD + 6th-order prolongation + worldtube at r~25M (in the AMR-refined region) + CCE via SpECTRE. Fixing only the extraction without fixing the evolution accuracy is pointless — and fixing only the evolution without CCE leaves gauge artifacts and missing GW memory.
