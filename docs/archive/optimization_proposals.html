Tier 1: Easy Wins Days

1 6th-order FD stencils 3-10x (coarser grid, same accuracy) Low-Med
What
Add 7-point 6th-order coefficients to finite_diff.h alongside the existing 5-point 4th-order ones. Compile-time or runtime flag selects order.
Why it works
For equivalent accuracy, 6th order needs N = N_4th^(2/3). An N=128 run at 4th order becomes N=40 at 6th order -- 33x fewer points, 3-10x after wider stencil overhead. AthenaK uses 6th-order as their standard NR config.
The current ghost width is already sufficient: 
// src/core/grid.h:17
#define GHOST_WIDTH 4   // 6th-order FD needs 3 ghost cells, KO-8 needs 4. Already covered.
The existing 4th-order stencil in finite_diff.h uses a 5-point stencil (offsets -2 to +2). A 6th-order stencil uses 7 points (offsets -3 to +3) -- still within ghost=4. No memory layout change. No new ghost exchange logic. Just new coefficients. 
// Current 4th-order (finite_diff.h:24-31) -- 5 points
return ((1.0/12.0)*f[idx-2*s] - (2.0/3.0)*f[idx-s]
      + (2.0/3.0)*f[idx+s] - (1.0/12.0)*f[idx+2*s]) / dx;

// Proposed 6th-order -- 7 points, same ghost budget
return (-1.0/60*f[idx-3*s] + 3.0/20*f[idx-2*s] - 3.0/4*f[idx-s]
      + 3.0/4*f[idx+s] - 3.0/20*f[idx+2*s] + 1.0/60*f[idx+3*s]) / dx;
2 Enable LTO (-flto in Makefile) 5-15% CPU Trivial
What
Add -flto to CFLAGS_OPT in the Makefile. One line. Enables link-time optimization across all translation units.
Why it works
The CPU hot path calls ccz4_rhs_point through a function pointer in a tight inner loop. Without LTO, GCC cannot inline across the backend_cpu.c / ccz4_rhs.c boundary, preventing constant propagation, SIMD, and loop optimizations.
No -flto anywhere in the Makefile. The hot path is a cross-TU function call: 
// Makefile:69 -- no LTO
CFLAGS_OPT = $(CFLAGS_BASE) -O3 -ffast-math -march=native

// backend_cpu.c:39-43 -- func is a function pointer, opaque to optimizer
for (int i = lo; i < hi; i++) {
    func(rhs, src, g, p, i, j, k);  // can't inline without LTO
}

With -flto, GCC sees that func is always ccz4_rhs_point, devirtualizes the call, and inlines the entire 500-line RHS function. The stencil loads, Christoffel symbols, and Ricci tensor computation all benefit from register allocation across the full call chain.

3 Fused d1/d2 stencil function 10-15% CPU, 5-10% GPU Low
What
Add fd_d1_d2() to finite_diff.h that computes both first and second derivatives in a single pass over the stencil points.
Why it works
fd_d1 and fd_d2 load the exact same 5 stencil points. For fields needing both derivatives (chi, lapse, h_ij, shift), we load each point twice. Fusing halves the memory loads.
// ccz4_rhs.c:87-109 -- d1 and d2 called separately, redundant loads
d1_chi[dir]      = fd_d1(src[FIELD_CHI], idx, s, dx);  // loads f[idx-2s..idx+2s]
...
d2_chi[dir][dir] = fd_d2(src[FIELD_CHI], idx, s, dx);  // loads same 5 points again
Counting from ccz4_rhs.c: chi needs d1+d2 (3 dirs each), lapse needs d1+d2, 6 h_ij components need d1+d2, 3 shift components need d1+d2. That is (1+1+6+3) x 3 = 33 pairs of redundant d1/d2 calls, each loading 5 doubles. The fused version saves ~165 redundant loads per point, about 10% of total memory traffic. 
// Proposed fused function for finite_diff.h
static inline void fd_d1_d2(const double *f, int idx, int s, double dx,
                             double *d1, double *d2) {
    double fm2=f[idx-2*s], fm1=f[idx-s], f0=f[idx], fp1=f[idx+s], fp2=f[idx+2*s];
    *d1 = ((1.0/12)*fm2 - (2.0/3)*fm1 + (2.0/3)*fp1 - (1.0/12)*fp2) / dx;
    *d2 = (-(1.0/12)*fm2 + (4.0/3)*fm1 - (5.0/2)*f0 + (4.0/3)*fp1 - (1.0/12)*fp2) / (dx*dx);
}
4 Checkpoint/restart N/A -- prevents losing 40-hour runs Low (~300 lines)
What
Raw binary checkpoint file with header (magic, version, N, L, step, time, params), per-block field data, and CRC32 footer. Ring buffer of 2 files. Checkpoint every 500 steps.
Why
Production inspiral runs take 10-40 hours. Without checkpointing, any crash loses everything. This is not optional for production use. The overhead is negligible: writing 342 MB every 500 steps is 0.2% of runtime, capping data loss at ~37 minutes.
Current output is 1D CSV slices only -- no way to resume from a crash: 
// output.c:31 -- only writes 1D CSV, no state persistence
fprintf(fp, "x,chi,lapse,K,Hamiltonian\n");
for (int i = g->ghost; i < g->ghost + g->N; i++) { ... }

Zero external dependencies (no HDF5, no ADIOS). Pure C with fwrite and a CRC32 implementation. The pack infrastructure already has meshblock_pack_load/meshblock_pack_store -- checkpoint piggybacks on the same pattern.

Tier 2: Moderate Effort 1-2 Weeks

5 Persistent pack (avoid per-step alloc/free) 10-20% GPU Medium
What
Create the meshblock_pack once and reuse it across timesteps. Invalidate only on mesh regridding.
Why it works
Currently, every single timestep allocates a pack, copies all field data in, runs kernels, copies data out, and frees the pack. For a 200-block AMR mesh at N=16, that is ~4 GB of memcpy per step -- pure overhead.
// rk4.c:623-661 -- pack built and destroyed EVERY step
static void ck45_step_mesh_packed(mesh_t *m, ...) {
    meshblock_pack_t *pack = mesh_build_leaf_pack(m, RK_CK45);  // alloc + memcpy
    backend_map_pack(pack, p);                                  // GPU map
    // ... 5 stages of actual work ...
    backend_unmap_pack(pack);                                    // GPU unmap
    meshblock_pack_store(pack, m->blocks);                       // memcpy out
    meshblock_pack_free(pack);                                   // free everything
}
meshblock_pack_create (meshblock_pack.c:93-158) allocates 3-4 page-aligned buffers of size NUM_FIELDS * n_blocks * npts doubles each. meshblock_pack_load (meshblock_pack.c:206-227) copies all fields from all blocks via memcpy loops. This entire lifecycle repeats per step -- and again per level during subcycling. For a static mesh between regrids, this is pure waste.
6 Selective GPU transfer (ghost slabs only) 3-8x transfer reduction Low-Med
What
During GPU ghost exchange, transfer only the ghost zone slabs (boundary cells) instead of the entire pack buffer.
Why it works
The GPU ghost exchange currently syncs the entire data buffer to host and back. For 200 blocks at N=16: that is 31 fields x 200 blocks x 13,824 points x 8 bytes = 687 MB round-trip. Ghost slabs are ~12% of that.
// backend_gpu.c:897-921 -- syncs EVERYTHING per ghost exchange
void backend_ghost_exchange_packed(meshblock_pack_t *pack) {
    size_t total = (size_t)pack->n_fields * pack->n_blocks * pack->npts;
    #pragma omp target update from(pack->data[0:total])  // ALL data: 342 MB
    // ... 5-phase exchange on host ...
    #pragma omp target update to(pack->data[0:total])    // ALL data back: 342 MB
}

Ghost zones at N=16 with ghost=4: each face slab is 4 x 24 x 24 = 2,304 points vs 13,824 total per block. With smart slicing, transfer drops from 342 MB to ~40-80 MB per exchange -- 4-8x reduction in PCIe traffic, which is the dominant GPU bottleneck.

7 Fused RHS + CK45 update 15-25% CPU, 10-20% GPU Medium
What
Instead of writing RHS to a separate buffer then reading it back for the CK45 update, fuse both operations inside ccz4_rhs_point. Eliminates the rhs buffer entirely.
Why it works
Currently each CK45 stage does: (1) write ~500 MB of RHS values, (2) read them back in the update kernel. Fusing avoids the intermediate buffer, saving one full memory pass per stage -- 5 stages = 5 GB of avoided bandwidth at N=128.
// Current: two separate operations per CK45 stage
// ccz4_rhs.c:480 -- writes to rhs buffer
rhs[FIELD_CHI][idx] = rhs_chi;

// backend_cpu.c:336-339 -- reads rhs buffer back in a second pass
scratch[i] = A_s * scratch[i] + dt * rhs_data[i];
data[i]   += B_s * scratch[i];

// Proposed: fuse inside the RHS kernel, no rhs buffer needed
// scratch[f][idx] = A_s * scratch[f][idx] + dt * rhs_chi;
// data[f][idx] += B_s * scratch[f][idx];

This also saves 25% memory for CK45 (eliminates the rhs buffer). The tradeoff: Sommerfeld BCs at boundary points need separate handling since they overwrite RHS values.

8 Larger AMR blocks (32^3) 1.7x from ghost overhead reduction Low
What
Support configurable block size, with 32^3 as the production default for GPU runs.
Why it works
At N=16 with ghost=4, each block is 24^3 = 13,824 total points but only 16^3 = 4,096 interior points. That means 70% of allocated memory is ghost zones -- wasted computation and bandwidth. At N=32, ghost overhead drops to 45%, and GPU occupancy improves dramatically (32,768 useful points per block vs 4,096).
Parthenon-VIBE (arXiv:2509.19701) warns that 16^3 blocks are at the lower boundary of GPU efficiency. AthenaK uses 64^3 for production. 
// block.c:85-86 -- N_block is already a runtime parameter
block_t *block_alloc(int id, int level, int N_block, double dx, ...) {
    double L_block = N_block * dx;
    b->grid = grid_alloc(N_block, L_block, method); // N_block must be multiple of 16
}

Effort is low because the block size is already a runtime parameter. The main work is testing that AMR regridding, prolongation, and restriction are correct at the new size.

9 CCZ3 formulation (Theta=0, kappa1=0) Stable to 10^5 M (100x longer runs) Low-Med
What
Add a --ccz3 mode that sets Theta=0 and kappa1=0 in all CCZ4 equations. Eliminates the Theta field and all constraint-damping Z-terms.
Why it works
arXiv:2501.01055 demonstrates that standard CCZ4 develops momentum-constraint-damping instabilities at late times. CCZ3 (their term for BSSN+Z4=0) is stable to 10^5 M. The direct compute saving is small (~4% fewer fields), but the science impact is massive: it unlocks multi-orbit inspirals that currently crash.
// ccz4_rhs.c:345-357 -- kappa1 terms that drive the late-time instability
if (p->ccz4.covariant_Z4)
    kappa1_times_lapse = p->ccz4.kappa1;         // sets magnitude of Z damping
else
    kappa1_times_lapse = p->ccz4.kappa1 * lapse;

double rhs_Theta = advec_Theta
    + 0.5 * lapse * (ricci.scalar - tr_A2 ...)
    - 0.5 * Theta * kappa1_times_lapse * ...  // <-- this term kills long runs

Implementation: runtime flag sets kappa1=0, skip Theta evolution, remove Z_over_chi contributions from Ricci and Gamma equations. Most changes are in ccz4_rhs.c with conditional branches (or compile-time #if).

Tier 3: Significant Effort Weeks

10 GPU-native ghost exchange 2-5x overall GPU speedup Med-High
What
Run the 5-phase ghost exchange as GPU kernels instead of syncing to host. Phase 1 (same-level) is device-to-device copies; Phases 2-4 are compute kernels.
Why it works
Ghost exchange is the #1 GPU bottleneck. Every RK stage currently does: GPU compute (fast) -> full sync to host (slow) -> CPU exchange (slow) -> full sync back (slow). Eliminating the host round-trip removes 684 MB of PCIe transfer per stage.
// backend_gpu.c:895-926 -- the entire exchange goes through host
void backend_ghost_exchange_packed(meshblock_pack_t *pack) {
    #pragma omp target update from(pack->data[0:total])  // GPU->CPU: ~342 MB
    packed_exchange_same_level(pack);    // CPU memcpy loops
    packed_restrict_to_coarse(pack);     // CPU compute
    packed_fill_coarse_buf_ghosts(pack); // CPU memcpy loops
    packed_fill_coarse_boundary(pack);   // CPU compute
    packed_prolongate_fine_ghosts(pack); // CPU compute
    #pragma omp target update to(pack->data[0:total])    // CPU->GPU: ~342 MB
}

Phase 1 is straightforward: precompute a work list of (src_offset, dst_offset, count) tuples on the host, map to device, run a flat copy kernel. Phases 2-4 are embarrassingly parallel per-point operations -- natural GPU kernels. The neighbor tables are already mapped to the device by backend_map_pack.

11 GPU kernel splitting for occupancy 20-40% GPU Med-High
What
Split ccz4_rhs_point into two stages: (1) compute all derivatives and store to intermediate buffer, (2) compute algebra, Christoffels, Ricci, and write RHS.
Why it works
The full RHS function uses ~400 registers per thread (all the derivative arrays, Christoffels, Ricci locals). On an A100 with 65,536 registers per SM, that is only ~163 threads per SM = ~15% occupancy. Splitting halves register pressure, doubling occupancy to ~30%.
// backend_gpu.c:215-216 -- the monster kernel, ~400 registers of locals
grid_t g_local;
memset(&g_local, 0, sizeof(grid_t));  // zeroes 872 bytes per thread (!)
Quick win within this proposal: replace the memset(&g_local, 0, sizeof(grid_t)) with targeted initialization of the 5 fields actually used (N, ghost, Ntotal, dx, npoints). This avoids zeroing 872 bytes per thread for a struct where only 40 bytes matter. Estimated 2-5% GPU speedup by itself.
12 3D output (raw binary + XDMF) N/A -- enables real science visualization Low (~200 lines)
What
Write raw binary field dumps with XDMF descriptor files. VisIt and ParaView load XDMF natively -- zero external library dependencies.
Why it works
The current output is 1D CSV slices along the x-axis. This is sufficient for 1D diagnostics but useless for visualizing 3D merger dynamics, gravitational wave extraction surfaces, or AMR mesh structure.
// output.c:31-32 -- current output: 1D CSV only
fprintf(fp, "x,chi,lapse,K,Hamiltonian\n");
// No 3D output capability exists.

Implementation: fwrite the raw field arrays (already contiguous in SoA layout), emit a short XML descriptor per snapshot. For AMR: one binary per block, XDMF describes the multi-block hierarchy. Optional async I/O thread (pthread + staging buffer) for high-frequency output without blocking compute.

Tier 4: Long-term Months

13 Multi-GPU support 1.5-3.5x on 4 GPUs Med-High
What
Split the meshblock_pack across multiple GPU devices. Each GPU gets a subset of Morton-ordered blocks with its own pack. Inter-device ghost exchange via host staging buffers.
Why it works
Single-GPU memory limits cap resolution. An A100 (80 GB) can handle ~100 blocks at N=32 with 31 fields. Splitting across 4 GPUs provides 4x memory and 3-3.5x throughput (after inter-device communication overhead).
The pack infrastructure already supports per-level packing (mesh_build_level_pack in rk4.c:754-798). Multi-GPU extends this to per-device packing. The Morton ordering in the mesh provides natural spatial locality for partitioning.
14 MPI domain decomposition Linear scaling with node count High (2-3 months)
What
Partition Morton-sorted leaf blocks across MPI ranks. Ghost exchange becomes intra-rank (memcpy, same as today) + inter-rank (MPI_Isend/Irecv with packed ghost buffers).
Why it works
The only path to cluster-scale runs. Single-node GPU limits resolution to N_eff ~ 512-1024. MPI enables N_eff > 4096 across hundreds of nodes. AthenaK demonstrates 80% scaling to 65,536 GPUs with this architecture (arXiv:2409.16053).

The subcycling complication: fine blocks needing coarse neighbor data across rank boundaries require temporal interpolation data to be communicated after each coarse step. This is the hardest part of the implementation. Estimated efficiency: 85-90% at 8 nodes, 70-80% at 64 nodes.

15 P-ERK multi-rate time integration 2-5x on AMR meshes High
What
Paired Explicit Runge-Kutta: different blocks use different numbers of RK stages based on local stiffness. Stiff blocks (near punctures) get many stages; outer blocks get few.
Why it works
Near a puncture, chi approaches zero and the effective CFL number is much smaller. CK45 wastes 5 full stages everywhere when only the blocks near punctures are stiff. P-ERK gives the outer 80% of blocks (which are non-stiff) fewer stages, saving 2-5x total work. Requires careful stage-matching at block boundaries.
// rk4.c:248-262 -- CK45 uses fixed 5 stages everywhere
static const double CK_A[5] = { ... };  // same coefficients for all blocks
static const double CK_B[5] = { ... };  // no per-block adaptation

Not Recommended Avoid

Mixed precision (float32 for intermediates) Against

Float32 Christoffel symbols accumulate ~1e-5 roundoff near punctures, which is comparable to N=256 truncation error. This would break 4th-order convergence -- the invariant that validates correctness. FP64 is non-negotiable for all physics arrays. The GPU kernel is compute-bound (not bandwidth-bound) anyway, so halving precision does not halve runtime.

Precomputed inverse metric Against

The inverse metric computation (compute_inverse_sym) is 30 FLOPs -- roughly 0.6% of the ~5,000 FLOPs in ccz4_rhs_point. Storing it as 6 extra evolved fields adds 48 bytes/point of memory bandwidth per RHS evaluation. On GPU, where the kernel is bandwidth-limited, this would be a net negative: saving 0.6% compute while adding ~3% bandwidth.

Operator splitting (split RHS into substeps) Against

Splitting the CCZ4 RHS into separate operators (e.g., advection step + source step) introduces splitting error that breaks the 4th-order convergence guarantee. The CCZ4 equations are tightly coupled -- Christoffel symbols, Ricci tensor, and gauge conditions all depend on each other at the same point and time. Strang splitting only recovers 2nd order at best.

Unified GPU memory Against

Page-fault-driven migration is unpredictable in a stencil code where neighboring threads access adjacent memory. Page faults during the RHS kernel would serialize GPU execution. GCC's OpenMP target support for unified memory is immature. Explicit mapping (already implemented) gives deterministic performance.

Task-based parallelism Against

5-15% potential benefit, 2-4 month effort, and it would fundamentally break the simple bulk-synchronous execution model. The current OpenMP parallel-for with pack batching is already well-matched to GPU execution. Subcycling already provides inter-level asynchrony. Adding a DAG scheduler adds complexity with marginal benefit.
