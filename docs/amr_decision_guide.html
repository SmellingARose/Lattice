4. Tier 1 — Essential

Tier 1: Must Build Cannot run multi-level AMR without these 7 components

block_t — Block Data Structure

Essential Easy

What

A struct wrapping grid_t with AMR metadata: refinement level, Morton index, tree links (parent, 8 children, 6 face-neighbors), boundary flags, and physical origin. Each block is a 16³ interior-cell cube with 4 ghost layers (24³ total = 13,824 points).

Why

AMR decomposes the domain into many small grids. block_t is the atom — every other component operates on blocks. Our existing ccz4_rhs_point() is already per-point, so it works unchanged inside a block's grid_t. This is the cleanest possible extension of the current architecture.

Difficulty

Easy — Pure data structure. Header + allocation/deallocation. ~150 lines of C. No algorithmic complexity.

If Skipped

Nothing works. There is no AMR without a block abstraction. The single-grid code cannot represent multiple resolution levels.

Evidence

Every AMR code has an equivalent: Athena++ MeshBlock, GRChombo FArrayBox, CarpetX GF_Data. The pattern is universal. Our version is simpler because we use a fixed block size (no variable-dimension boxes).

Athena++: Stone et al. 2020 (ApJS 249, 4), §3.1

Build in Stage 1. Foundation for everything else. ~2 hours.

mesh_t — Mesh Manager

Essential Medium

What

Top-level struct owning all blocks. Manages the oct-tree: creation of root-level blocks, refinement/coarsening operations, block lookup by ID, level iteration. Also holds domain parameters (L, dx_base, N_root) and simulation parameters. A single-block mesh must behave identically to the current grid_t path.

Why

Something must own and organize the blocks. mesh_t is the control plane — it decides which blocks exist, maintains the tree structure, and provides iteration over leaf blocks (the active ones holding data). The RK4 stepper calls mesh_t instead of a single grid_t.

Difficulty

Medium — Block lifecycle management, tree operations, backward compatibility. ~500 lines. The tricky part is ensuring the 1-block mesh path is exactly identical to the old code (for test compatibility).

If Skipped

Nothing works. Without a mesh manager, blocks are disconnected. No iteration, no tree, no AMR.

Evidence

Athena++ Mesh class is ~3000 lines of C++. Ours will be much smaller (no MPI, no load balancing, fixed block size). GR-Athena++ extends the base Mesh with NR-specific features (puncture tracking, constraint monitoring) — we can add those later.

Athena++: Stone et al. 2020 (ApJS 249, 4), §3.2

Build in Stage 1. The orchestrator. ~1–2 days.

Same-Level Ghost Exchange

Essential Medium

What

For each pair of face-neighboring blocks at the same level, copy 4 layers of interior cells from one block's boundary into the other's ghost zone (and vice versa). 25 fields × 6 faces × all leaf blocks. This is a direct memory copy — no interpolation needed since both blocks share the same dx.

Why

Finite difference stencils need data beyond each block's interior. Without ghost exchange, derivatives at block boundaries are wrong, producing O(1) errors that immediately blow up the simulation. Ghost exchange is what makes multi-block decomposition work at all.

Difficulty

Medium — Index arithmetic for 6 face orientations, each with a slab copy. Must handle all 25 fields × 4 ghost layers. ~300 lines. The concept is simple (memcpy slabs) but index details are easy to get wrong. Test by comparing multi-block results to single-grid.

If Skipped

Cannot decompose domain into blocks. Even a uniform-resolution multi-block mesh requires ghost exchange. FD stencils at block boundaries would read uninitialized memory.

Evidence

Athena++ ghost exchange validation: 64-block uniform mesh must match single-grid to roundoff (~1e-14 relative error). Any deviation indicates an indexing bug. GR-Athena++ uses the same face-exchange pattern with GHOST_WIDTH=4 for 4th-order FD.

Athena++: Stone et al. 2020, §4.2; GR-Athena++: Daszuta et al. 2021, §2.3

Build in Stage 2. The validation gate: multi-block = single-grid to roundoff. ~2–3 days.

Cross-Level Ghost Exchange

Essential Hard

What

When a fine block (level L+1) borders a coarse block (level L), the fine block's ghost zone needs data that doesn't exist at matching resolution on the coarse side. Solution: prolongate coarse data into fine ghosts (interpolate to finer spacing). The reverse direction: restrict fine data into the overlapping region of the coarse block's ghost zone. Execution order: coarsest level first, then finer, so prolongation always has coarse data available.

Why

Multi-level refinement is the whole point of AMR. Without cross-level ghost exchange, different-level blocks cannot communicate, and refinement boundaries become impenetrable walls where the solution is discontinuous.

Difficulty

Hard — The hardest single component. Must correctly identify which coarse cells contribute to each fine ghost cell, apply prolongation with the right stencil, handle the coarse-fine interface geometry (fine block face might cover only half a coarse block face). ~500 lines. This is where most AMR bugs live.

If Skipped

Cannot have multiple refinement levels. Limits you to uniform multi-block decomposition (Stage 2 only). No actual adaptive refinement.

Evidence

GRChombo spends significant effort on their FillPatch operation, which is exactly this. Carpet's dh.cc schedules ghost exchanges level-by-level. GR-Athena++ uses the base Athena++ prolongation/restriction infrastructure, which is ~2000 lines of C++ (we need a subset since we only have one grid type).

Athena++: Stone et al. 2020, §4.4; GRChombo: Andrade et al. 2021, §4.2

Build in Stage 4. The core of actual AMR. Budget ~1 week. Test exhaustively against single-grid.

Prolongation (Coarse → Fine)

Essential Medium

What

Interpolates coarse-grid field values onto a finer grid. Baseline: slope-limited linear interpolation with minmod limiter. For each fine cell, compute the value from the nearest coarse cell plus a limited gradient. The minmod limiter suppresses oscillations at sharp features (critical near punctures where chi has steep gradients).

Why

Used in two places: (1) filling fine-block ghost zones from coarse neighbors (every timestep), (2) initializing child blocks when refining (occasional). Without prolongation, there's no way to create fine-grid data from coarse-grid data.

Difficulty

Medium — Minmod in 3D with 2:1 ratio. ~200 lines. The interpolation math is straightforward, but getting the index mapping between coarse and fine cells correct (accounting for ghost offsets and physical coordinates) requires care.

If Skipped

No cross-level ghost exchange, no refinement. This is half of the cross-level ghost exchange machinery.

Evidence

Athena++ uses minmod for prolongation in MHD, citing stability advantages over higher-order schemes at discontinuities. GR-Athena++ inherits this. However: minmod is only 2nd-order accurate, which means refinement boundaries introduce O(dx²) error — a known limitation. BAM and GRChombo use higher-order prolongation for NR. See the Tier 3 card on 4th-order Lagrange for the upgrade path.

GR-Athena++: Daszuta et al. 2021, §2.3; BAM: Brugmann et al. 2008

Build minmod in Stage 3. Works, proven, simple. Upgrade to 4th-order later if convergence order degrades at refinement boundaries.

Restriction (Fine → Coarse)

Essential Easy

What

Volume-weighted average: each coarse cell gets the mean of the 2³ = 8 fine cells that overlap it. Conservative by construction (fine total = coarse total × 8). Used after fine-level time steps to update the coarse representation, ensuring the coarse grid reflects the higher-accuracy fine-grid solution.

Why

Without restriction, the coarse grid diverges from the fine grid over time. When fine blocks are later used to fill coarse ghost zones (or when coarse data is visualized/extracted), it would show stale, inaccurate values. Restriction keeps the hierarchy consistent.

Difficulty

Easy — Literally averaging 8 values. ~100 lines including the loop over all overlapping fine-coarse block pairs. The simplest AMR operation.

If Skipped

Coarse grid becomes inconsistent. Ghost zones filled from coarse data would be wrong. Constraint violations accumulate on coarse levels. Multi-level evolution becomes unstable within ~100 steps.

Evidence

Universal across all AMR codes. Simple volume-weighted averaging is the standard for cell-centered NR codes (Athena++, Carpet, BAM). Some codes use "injection" (just copy the coincident fine cell) — this is cheaper but not conservative. Volume averaging is safer for CCZ4.

Berger & Oliger 1984 (original AMR paper), §4

Build in Stage 3. Trivial implementation, critical for correctness. ~2 hours.

2:1 Level Constraint

Essential Medium

What

Enforce that no block's refinement level differs by more than 1 from any of its face-neighbors. If refining a block would create a 2-level jump, the intermediate neighbor must also be refined. This is also called the "proper nesting" or "grading" constraint. Applied after every regrid operation.

Why

Prolongation operators are designed for a 2:1 resolution ratio. A 4:1 jump (two levels) would require different interpolation stencils and produce much larger truncation error. The 2:1 constraint guarantees that every ghost exchange uses the same prolongation operator, simplifying the code and bounding the interpolation error.

Difficulty

Medium — After flagging blocks for refinement, iterate: if any newly refined block has a coarse neighbor (level difference > 1), flag that neighbor for refinement too. Repeat until converged. ~150 lines. Subtle: the cascade can propagate across the entire domain.

If Skipped

Interpolation blows up at 4:1 boundaries. Without the constraint, blocks at level 3 could neighbor blocks at level 1. The 2:1 prolongation operator would produce garbage, and constraint violations would grow exponentially.

Evidence

Athena++ enforces this in Mesh::AdaptiveMeshRefinement(). GRChombo enforces it via Chombo's BRMeshRefine. Every oct-tree AMR code enforces 2:1 grading. Codes that don't (like early Dendro-GR with wavelet-based adaptivity) use fundamentally different approaches to inter-level communication.

Athena++: Stone et al. 2020, §3.4

Build in Stage 4 alongside dynamic regridding. Relatively simple algorithm, non-negotiable for correctness.

5. Tier 2 — High Value

Tier 2: High Value Significant quality or performance improvements, most worth building soon after Tier 1

Morton (Z-Order) Encoding

High Value Easy

What

Bit-interleaving of (ix, iy, iz) block coordinates to produce a single int64_t Morton index. Provides a space-filling curve ordering of blocks with a key property: face-neighbors differ by exactly one bit-group, making neighbor lookup O(1) via bit manipulation instead of tree traversal.

Why

Fast neighbor finding is critical for ghost exchange (called every RK substep). Without Morton encoding, finding a block's 6 face-neighbors requires tree traversal or hash table lookup. With Morton encoding, neighbors are computed arithmetically in ~10 nanoseconds. Also provides natural load-balancing order for GPU batching.

Difficulty

Easy — ~80 lines. Bit-interleave function, decode function, 6 neighbor functions (increment/decrement each coordinate in Morton space). Well-documented algorithm with known bit tricks. Header-only.

If Skipped

Slower neighbor lookup. Would need a hash table or flat array search to find neighbors. Works but adds overhead to every ghost exchange call. For 1000+ blocks (N_BH ≥ 5), the O(N) search becomes noticeable.

Evidence

Morton encoding is fundamental to Athena++, AthenaK, and p4est (the standard oct-tree library). Used in Dendro-GR for spatial sorting. The bit-interleave pattern is well-established in computational geometry and database indexing.

Athena++: Stone et al. 2020, §3.3; p4est: Burstedde et al. 2011

Build in Stage 2. Tiny investment, large payoff. Unlocks efficient neighbor finding for all future stages.

Chi-Gradient Refinement Criterion

High Value Easy

What

Compute |∇χ| × dx at each interior point of each block. If the maximum exceeds a threshold chi_refine (e.g., 0.1), flag the block for refinement. If below chi_coarsen (e.g., 0.01) for all 8 siblings, flag for coarsening. Chi is the conformal factor that goes to zero at punctures, so its gradient naturally identifies where black holes are and how much resolution they need.

Why

AMR needs to know where to refine. The chi-gradient criterion is the simplest approach that works for arbitrary numbers of BHs: it doesn't need puncture positions, spin parameters, or mass ratios as input. It just measures where the spacetime curvature is steep and refines there.

Difficulty

Easy — ~80 lines. Loop over interior points, compute |∇χ| using existing FD macros, take max, compare to threshold. The thresholds need tuning per simulation, but the code is straightforward.

If Skipped

Must use static refinement. Without a criterion, someone must manually specify which regions to refine. This works for single-BH tests but fails for inspiraling binaries (the BHs move) and is impractical for N ≥ 3 bodies.

Evidence

GRChombo uses chi-gradient as their primary criterion. GR-Athena++ uses a similar approach. The alternative — truncation error estimation (see Tier 4) — is mathematically optimal but 2× more expensive. For most BBH simulations, chi-gradient gives the same block distribution as truncation error at half the cost.

GRChombo: Andrade et al. 2021, §5.1; arXiv:2312.05438 (refinement strategy comparison)

Build in Stage 4. Simple, proven, essential for dynamic AMR. The standard choice.

CAKO — Curvature-Adjusted KO Dissipation

High Value Easy

What

Scale Kreiss-Oliger dissipation by the conformal factor W = χ: sigma_CAKO = chi * sigma_base. Near punctures where χ → 0, dissipation vanishes (preserving physical gradients). In the wave zone where χ ≈ 1, full dissipation is applied (suppressing interpolation noise from refinement boundaries).

Why

Standard constant-sigma KO dissipation has a fatal tension in AMR: you need strong dissipation to suppress noise at refinement boundaries, but strong dissipation near punctures damps the physical solution. CAKO resolves this by making dissipation spatially adaptive to the curvature — strong where noise is bad, weak where physics is sharp.

Difficulty

Easy — One line of code. Multiply sigma by chi in dissipation.c. No new files, no new data structures, no architectural changes. The hardest part is reading the paper to understand why it works.

If Skipped

2–5 orders of magnitude more constraint noise at refinement boundaries. The simulation will still run, but Hamiltonian constraint violations in the wave zone will be 10,000× larger. This contaminates gravitational wave extraction (Psi4). For N ≥ 3 bodies, the accumulated noise may destabilize the evolution.

Evidence

arXiv:2404.01137 (Etienne 2024): validated across 100+ BBH configurations (q=1–6, spin up to 0.5). Strong-field Hamiltonian violations reduced by 2 OOM, wave-zone violations by 5 OOM. Available in Einstein Toolkit's BaikalVacuum thorn but not yet adopted by GRChombo, GR-Athena++, or BAM. The paper uses 9th-order KO on an 11-point stencil with sigma_base = 0.99 for gauge, 0.3 for others; we can start with our existing 6th-order stencil.

arXiv:2404.01137 (Etienne 2024), §II.A, Fig. 2

Build in Stage 3. Highest value-to-effort ratio of any component. One line = 5 OOM improvement. No reason not to.

Dynamic Regridding

High Value Medium

What

Every N_regrid steps (e.g., 10), re-evaluate the refinement criterion on all blocks, flag blocks for refinement or coarsening, enforce the 2:1 constraint, then actually split/merge blocks. Includes the refine operation (1 block → 8 children: allocate, prolongate, update tree) and coarsen operation (8 children → 1 parent: restrict, deallocate, update tree).

Why

BHs move. During inspiral, the BH trajectories sweep through the domain. Static refinement centered on the initial positions becomes useless once the BHs move more than ~2 blocks. Dynamic regridding tracks the BHs automatically, maintaining high resolution where it's needed at each moment.

Difficulty

Medium — Refine/coarsen operations plus tree bookkeeping. ~400 lines. Main subtleties: ensuring the tree stays consistent during split/merge (no dangling pointers), and that regridding doesn't introduce transient noise (because newly created fine blocks have prolongated — not evolved — data).

If Skipped

Static refinement only. Must know BH positions in advance and pre-refine. Works for single BH tests (BH doesn't move) and short head-on collisions. Unusable for inspirals (BHs orbit for 10+ cycles before merging) and N-body (trajectories are chaotic).

Evidence

GRChombo regrids every ~10 steps. Athena++ regrids with a configurable interval. Carpet regrids every coarse time step. Too frequent regridding wastes time; too infrequent loses track of moving features. N_regrid = 10 is the standard starting point.

GRChombo: Andrade et al. 2021, §5.2; Carpet: Schnetter et al. 2004

Build in Stage 4 alongside chi-gradient and 2:1 constraint. Required for binary inspiral (Milestone 5).

Time Subcycling

High Value Hard

What

Each refinement level uses its own timestep: dt_L = CFL × dx_L. Level L+1 takes 2 steps for every 1 step at level L (since dx is halved). A 6-level hierarchy does 32 fine steps per 1 coarse step. Without subcycling, all levels use dt = CFL × dx_finest, meaning coarse blocks (with few cells) take tiny, wasteful steps.

Why

Performance only. With 6 levels, global dt is 32× smaller than the coarse level's CFL limit. The coarse level has relatively few blocks, so the wasted work is proportional to (# coarse cells) × 31 unnecessary steps. For a typical 2-BH run with ~200 blocks, the coarse level might have 50 blocks — so global dt wastes 50 × 31 = 1550 extra block-steps per coarse step. Whether this matters depends on the fine-level cost.

Difficulty

Hard — Recursive scheduling: advance fine levels, restrict to coarse, fill coarse ghosts, advance coarse. Must synchronize data at level boundaries after each sub-step. Inter-level ghost exchange timing becomes critical. ~600 lines. The scheduling logic is conceptually clean but implementation details (when to restrict, when to fill ghosts, how to handle regridding mid-cycle) are tricky.

If Skipped

Higher cost per wall-clock second. All blocks advance at the finest dt. For 4–6 levels this is a 8–32× overhead on coarse blocks. In practice, coarse blocks are a small fraction of total blocks (most blocks are at the finest level near BHs), so the actual overhead is typically 2–5× for typical BBH runs. Athena++ itself supports both modes.

Evidence

GRChombo, Carpet, and BAM all subcycle. AthenaK uses global dt (GPU efficiency favors fewer, larger kernel launches). Dendro-GR uses global dt. The performance benefit depends on the ratio of coarse to fine blocks — for N ≥ 5 BHs with many fine regions, global dt becomes more competitive because most blocks are fine anyway.

Carpet: Schnetter et al. 2004; Athena++ (both modes): Stone et al. 2020, §4.5

Defer to Stage 5. Start with global dt (simpler, proven by AthenaK). Add subcycling later only if profiling shows coarse-level waste is a bottleneck. For GPU targets, global dt may actually be preferred.

MeshBlockPack GPU Batching

High Value Hard

What

Pack all leaf blocks at the same level into a single contiguous buffer: pack[field][block_idx][k][j][i]. Dispatch one GPU kernel over (N_blocks × N_points) threads instead of N_blocks separate kernel launches. Ghost exchange also executed on-device (pack boundary slabs into send/receive buffers without host round-trips).

Why

GPU kernel launch overhead dominates at small block sizes (16³ = 4096 points). Launching 500 separate kernels for 500 blocks wastes ~5 ms per RK substep in launch overhead alone. Batching into 1 kernel eliminates this, achieving full GPU occupancy. This is the AthenaK innovation that made oct-tree AMR competitive with block-structured on GPUs.

Difficulty

Hard — New memory layout for packed buffers, modified kernel dispatch, on-device ghost exchange. ~800 lines. Must ensure the packed layout is compatible with existing FD macros (or provide a thin adapter). The pack/unpack operations add some overhead that must be amortized over the kernel execution.

If Skipped

GPU backend works but is 5–10× slower. Per-block kernel launches kill throughput on GPUs. The CPU backend (OpenMP threads) is fine without batching since there's no launch overhead. If GPU performance isn't needed yet, this can wait.

Evidence

AthenaK benchmarks: MeshBlockPack achieves 90% of theoretical peak on A100 for GRMHD (comparable physics complexity to CCZ4). Without packing, they measured 10–15% utilization due to launch overhead. Dendro-GR uses a similar "batch all blocks" approach for GPU execution.

AthenaK: Grete et al. 2024 (arXiv:2409.16053), §4.2, Fig. 5

Defer to Stage 6. Get AMR working on CPU first. Add GPU batching only when ready for production GPU runs. The CPU backend has no launch overhead problem.

6. Tier 3 — Nice to Have

Tier 3: Nice to Have Measurable improvements but not blocking — add when the basic system works

4th-Order Lagrange Prolongation

Nice to Have Medium

What

Upgrade prolongation from minmod (2nd-order) to 4th-order Lagrange polynomial interpolation. Uses a 4-point stencil in each direction (vs minmod's 2-point) to achieve accuracy matching the 4th-order FD scheme. No limiter — relies on CAKO + CAHD to control oscillations near punctures instead.

Why

Minmod prolongation is only 2nd-order, creating a bottleneck at refinement boundaries that can degrade global convergence order from 4 to ~2–3. With 4th-order prolongation, the interpolation error matches the FD truncation error, and refinement boundaries become nearly invisible in convergence tests. Every mature NR code that uses 4th-order FD also uses ≥ 3rd-order prolongation.

Difficulty

Medium — ~250 lines. The Lagrange interpolation formula is standard, but implementing it in 3D with correct index offsets for the coarse-fine mapping requires care. Must handle boundaries of the coarse stencil (need 2 coarse cells on each side of the interpolation point). This increases the effective ghost width requirement from 1 to 2 coarse cells per prolongation layer.

If Skipped

Local convergence order drops to ~2 at refinement boundaries. Global convergence typically stays 3–3.5 (the 4th-order interior dominates). For gravitational wave extraction far from boundaries, this is usually fine. For constraint monitoring near refinement boundaries, the degradation is visible.

Evidence

BAM uses 5th-order Lagrange prolongation. GRChombo uses 4th-order. Carpet defaults to 3rd-order (quadratic). All experienced convergence degradation before upgrading. The key finding: with CAKO suppressing interpolation noise, higher-order prolongation doesn't cause oscillation problems that motivated minmod in the first place.

BAM: Brugmann et al. 2008, §3.3; GRChombo: Andrade et al. 2021, §4.3

Defer to after Stage 4. Start with minmod (proven, stable). Upgrade to 4th-order Lagrange after measuring convergence order at refinement boundaries. If global order stays ≥ 3.5, minmod is fine. If it drops below 3, upgrade.

CAHD — Coarse-Grid-Adjusted Hamiltonian Damping

Nice to Have Easy

What

Scale constraint damping by refinement level: kappa1_CAHD = kappa1_base * 2^(level_max - level). Coarser grids get exponentially stronger damping. At 5 levels of refinement, the coarsest grid has 32× the base kappa1.

Why

Constraint violations accumulate worst on coarser grids (bigger cells = larger truncation error, plus prolongation injects noise from above). Standard constant kappa1 doesn't account for this. CAHD targets the damping where the problem is worst. Synergistic with CAKO: CAKO reduces noise generation, CAHD accelerates noise absorption.

Difficulty

Easy — One line of code. Multiply kappa1 by 1 << (max_level - block_level) in ccz4_rhs.c. The block's level must be accessible in the RHS function (pass via params or a per-block field). No new files, no architectural changes.

If Skipped

Momentum constraint violations 3 OOM larger on coarse grids. The simulation still runs (CCZ4's constraint damping still works, just at the base rate). For short evolutions (< 1000M) or few levels (≤ 3), the effect is small. For long evolutions with 6+ levels, the accumulated violation becomes significant.

Evidence

arXiv:2404.01137 (Etienne 2024): 3 OOM reduction in momentum constraints. Tested across 100+ BBH configurations. Effect becomes more important with more refinement levels. Not used by GRChombo, GR-Athena++, or BAM (they pre-date this paper). Easy to A/B test: run the same simulation with and without CAHD, compare constraint norms.

arXiv:2404.01137 (Etienne 2024), §II.B, Fig. 3

Build in Stage 3 alongside CAKO. One line of code, significant constraint improvement. The only reason it's Tier 3 instead of Tier 2 is that it's less impactful than CAKO (3 OOM vs 5 OOM) and only matters with AMR (CAKO also helps single-grid). Given the trivial implementation, just do it.

SSL — Slow-Start Lapse

Nice to Have Easy

What

Temporary damping of the initial gauge pulse during early evolution. The 1+log gauge generates a sharp superluminal pulse at √2·c from each puncture. When this pulse crosses AMR refinement boundaries, it reflects and generates noise. SSL adds a time-dependent damping term:
dt(α) = [standard] - W · h · exp(-t²/(2σ_t²)) · (α - W)
with h = 0.6M, σ_t = 20M. The damping is exponentially negligible after t ≈ 170M.

Why

The initial gauge pulse is a non-physical transient that exists in every moving-puncture evolution. On uniform grids, it just propagates outward and exits through the boundary. With AMR, it reflects at every refinement boundary, contaminating the solution. SSL smooths the pulse so it doesn't have sharp features to reflect.

Difficulty

Easy — ~5 lines in the gauge section of ccz4_rhs.c. Add the SSL term to rhs_lapse, with two parameters (h, sigma_t) that can be hardcoded or added to params. Completely transparent after t > 170M.

If Skipped

4.3× more noise in dominant GW mode during early evolution. The gauge pulse noise decays over time as the pulse exits the domain, but for the first ~200M of evolution, it contaminates Psi4 extraction. Higher-order GW modes (l ≥ 4) may be below the noise floor without SSL. For short evolutions where only the merger waveform matters, this is acceptable.

Evidence

arXiv:2404.01137 (Etienne 2024): 4.3× noise reduction in dominant (l=2, m=2) GW mode. Higher modes show even more improvement (previously undetectable modes become visible). Effect is purely during the initial transient — no impact on the gauge dynamics at late times. Only relevant for AMR; on uniform grids, the pulse propagates cleanly.

arXiv:2404.01137 (Etienne 2024), §II.C, Fig. 4

Build in Stage 3. Tiny code change, measurable improvement in GW accuracy. Easy to A/B test. Not blocking, but the cost is so low that deferring makes no sense.

Dense Output (CarpetX Trick)

Nice to Have Hard

What

When subcycling, fine and coarse levels aren't time-synchronized: the coarse level is at time t while the fine level needs coarse data at t + dt_fine. "Dense output" uses the RK method's intermediate stages to construct a continuous time interpolation polynomial, providing coarse data at any intermediate time to 4th-order accuracy. CarpetX implements this for Berger-Oliger subcycling.

Why

Without dense output, subcycling uses the coarse solution at time t (or linearly interpolates between t and t+dt_coarse) to fill fine ghost zones at intermediate times. This introduces O(dt²) temporal error at refinement boundaries, reducing global time integration accuracy from 4th to 3rd order. Dense output maintains 4th-order accuracy.

Difficulty

Hard — Requires storing all RK stages for each block (not just the current solution and RHS), computing the dense output polynomial coefficients, and evaluating them at arbitrary intermediate times. ~400 lines. Conceptually straightforward for CK45 (which has known dense output coefficients) but significantly complicates the time stepper code.

If Skipped

Temporal order at refinement boundaries drops from 4 to 3. Only relevant if subcycling is implemented (with global dt, all levels are synchronized). BAM operates at 3rd-order temporal accuracy at boundaries and produces science-grade waveforms. The 4th-to-3rd reduction is measurable but not catastrophic.

Evidence

CarpetX (Schnetter 2022) implements dense output for their Berger-Oliger subcycling, achieving 4th-order accuracy across levels. BAM doesn't use it and operates at 3rd order at boundaries. GRChombo doesn't use it either. The consensus is that spatial interpolation error (prolongation) dominates over temporal interpolation error, so this is low priority.

CarpetX: github.com/eschnett/CarpetX (2022); BAM: Brugmann et al. 2008

Defer indefinitely. Only relevant with subcycling, and even then, 3rd-order temporal accuracy at boundaries is usually sufficient. Build only if convergence tests show temporal error dominating spatial error at refinement boundaries.

Per-Field Dissipation Strength

Nice to Have Easy

What

Use different KO dissipation strengths for different field groups: higher sigma for gauge variables (lapse, shift, B^i) which evolve faster and generate more noise, lower sigma for constraint-propagating variables (Theta, Gamma^i) where excessive dissipation can suppress constraint damping. Etienne 2024 uses sigma = 0.99 for gauge, 0.3 for others.

Why

Gauge variables are the noisiest (the 1+log and Gamma-driver conditions have characteristic speeds > c) and benefit most from strong dissipation. But applying sigma = 0.99 to physical variables like h_ij and A_ij would over-damp them. Per-field sigma allows optimal dissipation for each variable type.

Difficulty

Easy — Change sigma from a single scalar to a per-field array (25 entries). Modify the dissipation loop to look up sigma_field[f] instead of a constant. ~20 lines changed. The values themselves need tuning via constraint convergence tests.

If Skipped

Sub-optimal dissipation trade-off. A single sigma that's good for gauge variables will over-damp physical variables (and vice versa). The current sigma = 0.3 works for both but isn't optimal for either. The effect is measurable in constraint norms but unlikely to cause instability.

Evidence

arXiv:2404.01137 uses sigma = 0.99 for gauge, 0.3 for everything else. Einstein Toolkit's BaikalVacuum thorn implements this. GRChombo and GR-Athena++ use a single sigma for all fields. The per-field approach is newer and less widely adopted.

arXiv:2404.01137 (Etienne 2024), §II.A, Table 1

Defer to after CAKO is working. Easy change, but requires tuning. Add it if CAKO alone doesn't sufficiently suppress gauge noise, or if constraint convergence tests show gauge variables dominating the error.

Direct Edge & Corner Ghost Exchange

Nice to Have Medium

What

Fill ghost zone edges (12 per block) and corners (8 per block) by direct copy from diagonally-adjacent blocks, rather than relying on sequential face exchanges to propagate data through edges/corners. Face exchange alone requires 3 passes (x, then y, then z) to fill edge and corner ghosts transitively.

Why

The 3-pass face-exchange approach works but is serial (can't parallelize the 3 directions). Direct edge/corner exchange allows all 26 neighbors (6 face + 12 edge + 8 corner) to communicate in a single parallel pass. This matters for GPU execution where synchronization barriers between passes are expensive.

Difficulty

Medium — ~300 lines. Must identify all 26 neighbors for each block (not just 6 face-neighbors). Edge and corner neighbors at different refinement levels require special handling. The index arithmetic is tedious but well-defined.

If Skipped

3-pass face exchange works correctly. Slightly slower due to 3 serial passes instead of 1 parallel pass. On CPU, the difference is negligible. On GPU with many blocks, the 3 synchronization barriers add ~0.5 ms per exchange. For < 500 blocks, this is under 1% of step time.

Evidence

Athena++ uses the 3-pass approach (face only, 3 communication rounds). AthenaK adds direct edge/corner exchange for GPU efficiency. GRChombo handles edges/corners via Chombo's ghost fill machinery. For our initial CPU implementation, the 3-pass approach is fine.

AthenaK: Grete et al. 2024, §4.1

Defer to Stage 6 (GPU optimization). The 3-pass face exchange is correct, simple, and fast enough for CPU. Add direct edge/corner exchange only if GPU profiling shows ghost exchange as a bottleneck.

7. Tier 4 — Probably Skip

Tier 4: Probably Skip High effort, marginal value, or superseded by our architecture choices

Truncation Error Refinement Criterion

Probably Skip Hard

What

Estimate the local truncation error by computing the solution on the current grid and a coarsened copy (2× dx), then measuring the difference. Where the difference exceeds a threshold, refine. This is mathematically the optimal refinement criterion — it directly measures what AMR is trying to reduce.

Why

Chi-gradient is a proxy for truncation error (regions of steep chi are also regions of large truncation error). Truncation error estimation is the "ground truth" — it doesn't require choosing which variable to monitor or what gradient threshold to use. It automatically adapts to any source of error, not just curvature.

Difficulty

Hard — Must compute RHS on a coarsened copy of each block (restrict to half resolution, compute RHS, compare). This doubles the RHS cost at regridding time. ~400 lines plus a coarsened-grid RHS evaluation framework. The coarsening must respect ghost zones and boundary conditions.

If Skipped

Use chi-gradient instead. For BBH, chi-gradient produces nearly identical refinement patterns to truncation error estimation (because the dominant error source is the BH curvature). For exotic physics where error comes from non-curvature sources (e.g., electromagnetic fields in Phase 2), truncation error might refine differently. But by then, we can add field-specific criteria.

Evidence

arXiv:2312.05438 compared chi-gradient, truncation error, and box-in-box refinement for BBH. Result: chi-gradient and truncation error produce the same block distribution for BBH, but chi-gradient is 2× cheaper. Dendro-GR uses truncation error (it's natural for wavelet-based AMR). GRChombo and Carpet use truncation error as an option but recommend simpler criteria for production BBH runs.

arXiv:2312.05438 (2024), §4, Fig. 8

Skip for Phase 1. Chi-gradient gives the same result at half the cost for BBH. Revisit only if Phase 2 physics (electromagnetic fields) introduces non-curvature error sources that chi-gradient can't detect.

Vertex-Centered Discretization

Probably Skip Hard

What

Store field values at grid vertices (cell corners) instead of cell centers. At refinement boundaries, coarse and fine grids share coincident vertices, so no interpolation is needed at those points — the fine grid simply copies the coarse value exactly. GR-Athena++ uses this approach.

Why

Reduces interpolation error at refinement boundaries by eliminating interpolation at shared vertices. The remaining interpolation (for non-coincident fine-grid points) is better conditioned because it has an exact anchor point.

Difficulty

Hard — Architectural change. Our entire codebase (grid layout, FD stencils, initial data, diagnostics, output) assumes cell-centered storage. Switching to vertex-centered would require modifying every component. This is a design decision that should have been made at the start; retrofitting it is a rewrite.

If Skipped

More interpolation error at refinement boundaries. Cell-centered is the standard for most NR codes (GRChombo, BAM, Carpet, Dendro-GR). CAKO + CAHD + SSL address the same noise problem through different means. GR-Athena++ chose vertex-centered partly because Athena++ was already vertex-centered for MHD reasons (divergence-free constraint).

Evidence

GR-Athena++ uses vertex-centered and reports good boundary behavior. But they also note that their approach requires special treatment at block corners and edges. GRChombo, BAM, Einstein Toolkit, and Dendro-GR all use cell-centered and produce science-grade results. The choice is a trade-off, not a clear winner.

GR-Athena++: Daszuta et al. 2021, §2.1; Athena++: Stone et al. 2020, §2.2

Skip. Architectural change to an already-working codebase. CAKO + CAHD + SSL achieve similar noise reduction without touching the discretization. Not worth the rewrite.

Flux Correction / Refluxing

Probably Skip Hard

What

At refinement boundaries, replace the coarse-grid flux with the sum of fine-grid fluxes, ensuring conservation across the interface. Standard in hydro/MHD AMR (AMReX, Chombo, Athena++). For NR, this means matching the CCZ4 "fluxes" (advection terms) at coarse-fine interfaces.

Why

Ensures conservation of evolved quantities across refinement boundaries. In hydro, this prevents mass/energy from "leaking" at interfaces. In NR, the analogous conservation is less clear — the CCZ4 system isn't written in conservative form, and the evolved quantities (h_ij, K, etc.) don't have a clear conservation interpretation.

Difficulty

Hard — Must identify and store fluxes at coarse-fine interfaces, accumulate fine-grid flux contributions, and apply the correction. ~500 lines. Requires the CCZ4 system to be decomposable into flux + source form, which it isn't naturally (the non-principal part contains Christoffel terms that aren't fluxes).

If Skipped

No conservation at refinement boundaries. For vacuum NR, this is fine — constraint damping (CCZ4's Theta and Z_i) serves a similar role by actively correcting violations. BAM's experience: flux correction helps at refinement boundaries but only for the principal part, and source terms remain unmatched. The benefit is marginal compared to CAKO/CAHD.

Evidence

BAM implemented flux correction for BSSN and found partial improvement (principal terms only). GRChombo inherits refluxing from Chombo but notes it's "not essential for vacuum spacetimes." Einstein Toolkit (Carpet) doesn't use flux correction for NR. GR-Athena++ and Dendro-GR don't use it. The consensus: flux correction matters for matter (neutron star mergers) but not for vacuum BH spacetimes.

BAM: Brugmann et al. 2008, §3.4; GRChombo: Andrade et al. 2021, §4.4

Skip for Phase 1 (vacuum BH only). Revisit in Phase 2 only if adding matter coupling. CAKO + CAHD handle the boundary noise that flux correction would partially address.

Buffer Zones

Probably Skip Medium

What

Add extra "buffer" blocks around refined regions — blocks that are refined not because they need high resolution, but to push the refinement boundary farther from the physics. GRChombo uses 3-block-wide buffers around each refined region. The idea is that interpolation error decays with distance from the boundary.

Why

Refinement boundary noise is worst right at the boundary. By adding buffer blocks, the important physics (BH, GW extraction sphere) is farther from the noise source. This is the brute-force approach to the same problem that CAKO/CAHD/SSL solve elegantly.

Difficulty

Medium — Modify the refinement criterion to expand flagged regions by N_buffer blocks in each direction. ~100 lines. The cost is in memory and compute: 3-block-wide buffers roughly double the number of blocks at each level.

If Skipped

No wasted blocks. Without buffers, every refined block is there because the physics demands it. CAKO + CAHD + SSL reduce boundary noise directly, making buffers redundant. The only case for buffers is if CAKO alone is insufficient.

Evidence

GRChombo uses 3-block buffers and still reports significant boundary noise. This suggests buffers alone aren't enough — you still need dissipation strategies. arXiv:2404.01137's CAKO achieves better noise reduction than GRChombo's buffers. Buffer zones are the "old" approach; CAKO/CAHD/SSL are the "new" approach.

GRChombo: Andrade et al. 2021, §5.2; arXiv:2404.01137, §I

Skip. Buffer zones trade memory for noise reduction that CAKO/CAHD/SSL achieve for free. If those techniques work as reported, buffers are pure waste.

Box-in-Box Refinement

Probably Skip Medium

What

Pre-defined nested cubes of increasing resolution centered on each BH. Each level is a single large box (not decomposed into oct-tree blocks). The classic "Carpet-style" approach: level 0 covers the whole domain, level 1 is a box around both BHs, level 2 has two boxes (one per BH), etc. No adaptivity — the box positions/sizes are specified in the parameter file.

Why

Simpler than adaptive oct-tree AMR: no refinement criterion, no regridding, no 2:1 constraint enforcement. Each level is a contiguous array (no block decomposition overhead). Good for well-understood configurations where BH trajectories are roughly known.

Difficulty

Medium — Different architecture from oct-tree. Would need a separate refinement path or a hybrid system. Implementing box-in-box alongside oct-tree adds complexity without sharing much code.

If Skipped

Use oct-tree with static refinement for the same effect. An oct-tree mesh can approximate box-in-box by statically refining blocks in a cube pattern. The result is identical physics with slightly more memory overhead (block boundaries within each "box"). The overhead is ~20% at 16³ block size.

Evidence

arXiv:2312.05438 compared box-in-box, sphere-in-sphere, and adaptive refinement for BBH. Box-in-box uses 2.5× more cells than sphere-in-sphere for the same accuracy. For N ≥ 3 BHs, box-in-box becomes impractical (overlapping boxes, wasted cells in empty space between BHs). The oct-tree approach subsumes box-in-box as a special case.

arXiv:2312.05438 (2024), §3, Table 2

Skip. Oct-tree with static refinement provides the same capability with the same code. Box-in-box is a dead-end architecture that doesn't scale to N ≥ 3.

Per-Block GPU Kernels

Probably Skip Medium

What

Launch a separate GPU kernel for each block's RHS evaluation, rather than batching all blocks into a single kernel (MeshBlockPack). Each block gets its own #pragma omp target teams distribute region.

Why

Simpler to implement than MeshBlockPack — just wrap the existing single-block kernel dispatch in a loop over blocks. No pack/unpack, no new data layout. Could serve as an intermediate step before full batching.

Difficulty

Medium — ~100 lines. Loop over blocks, dispatch each one. Must manage data transfers (upload each block's fields to GPU, download results). The data transfer overhead is the bottleneck.

If Skipped

Go directly to MeshBlockPack. Per-block kernels are the wrong approach for GPUs — the launch overhead and data transfer latency dominate. AthenaK's benchmarks show 10–15% GPU utilization without batching. It's better to skip this and invest the time in MeshBlockPack directly.

Evidence

AthenaK explicitly abandoned per-block kernels in favor of MeshBlockPack, citing unacceptable launch overhead. Dendro-GR uses a similar batch approach. No modern GPU AMR code uses per-block kernels in production.

AthenaK: Grete et al. 2024, §4.2

Skip. Per-block GPU kernels are a known anti-pattern. If GPU execution is needed, build MeshBlockPack (Tier 2) directly.

Static Refinement (Manual Specification)

Probably Skip Easy

What

Allow the user to manually specify which regions to refine (e.g., "refine all blocks within radius R of point P to level L"). Refinement is fixed at initialization and never changes during evolution. No criterion evaluation, no regridding.

Why

Useful for debugging and testing: test 2-level ghost exchange without needing the full regridding machinery. Also useful for single-BH tests where the BH doesn't move.

Difficulty

Easy — ~50 lines. Parse a region specification, refine matching blocks at initialization. No ongoing maintenance.

If Skipped

Use chi-gradient from the start. The chi-gradient criterion at initialization produces the same refinement pattern as "refine around the puncture" — it just determines the pattern automatically. Static refinement is a convenience, not a necessity. For testing, we can use chi-gradient with regridding disabled (flag once, never re-evaluate).

Evidence

Carpet supports static refinement via parameter files. GRChombo supports it as "fixed boxes." Both primarily use it for testing and simple configurations. For any production run, adaptive refinement is preferred.

Carpet: Schnetter et al. 2004, §3.1

Skip as a dedicated feature. Use chi-gradient with regrid_every=0 (evaluate once at t=0, never update) for the same effect. Saves implementing a separate code path.
