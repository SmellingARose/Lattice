Debugging case study. How a 4-line loop-bound change fixed a 4000x error in the AMR ghost exchange pipeline. Covers the wrong turns, the root cause analysis, and the generalizable debugging methodology.
Last updated: 2026-02-17  |  Source: src/amr/ghost_exchange.c  |  Companion: Coarse-Buffer Ghost Exchange

Introduction: AMR Ghost Exchange

In an adaptive mesh refinement (AMR) simulation, blocks at different refinement levels share boundaries. When a fine block (level L+1) neighbors a coarser block (level L), the fine block's ghost cells need data that does not exist at fine resolution. The multi-level ghost exchange solves this by interpolating coarse data into fine ghost zones through a 5-phase pipeline.

Lattice implements the AthenaK coarse-buffer architecture: each fine block carries a private half-resolution buffer (coarse_buf) that is filled with restricted fine data (Phase 2), given proper ghost zones from neighbors (Phase 3) and boundary extrapolation (Phase 3.5), then prolongated back into the fine block's ghost cells (Phase 4). The full pipeline is documented in the companion deep-dive.

This case study tells the story of a bug in Phase 3.5 that took three debugging attempts to find.

The Symptom: Test 6 Fails with O(1) Error

After implementing the coarse-buffer architecture (AMR Stage 4.1), all tests passed except Test 6: "Multi-level ghost exchange polynomial accuracy." The test creates a 2x2x2 mesh, refines one block to level 1, sets a polynomial f = 1 + 0.001*(x^2 + y^2 + z^2) on all blocks, runs ghost_exchange_multilevel(), then checks that fine ghost cells match the analytic polynomial.

Test 6 FAIL: max_err = 0.386, threshold = 9.8e-5. The error was 4000x above the acceptable limit. This is an O(1) error — not a convergence order problem, but a fundamental data-filling failure.

The error magnitude immediately ruled out numerical precision issues or stencil-order problems. Something was reading garbage data.

Wrong Diagnosis #1: Blame the Extrapolation Coefficients

Phase 3.5 uses 3-point Lagrange extrapolation to fill domain-boundary ghost cells. The coefficients for distance d from the boundary are derived from evaluating the Lagrange basis at -d:

d=1: ghost = 3*f[0] - 3*f[1] + 1*f[2]
d=2: ghost = 6*f[0] - 8*f[1] + 3*f[2]

First hypothesis: the extrapolation coefficients {3, -3, 1} and {6, -8, 3} were wrong, or quadratic extrapolation was the wrong approach entirely. Maybe flat copy (zeroth-order, just replicate the boundary cell) would be more stable.

Test: Replaced quadratic extrapolation with flat copy (ghost[d] = interior[0]). Same error: max_err = 0.386. The extrapolation coefficients were irrelevant — the bug was not about how the cells were filled, but about which cells were filled at all.

Wrong Diagnosis #2: Maybe Our Approach is Fundamentally Wrong

Second hypothesis: perhaps the AthenaK/Athena++ pattern requires a different boundary treatment that we had not implemented. Time to re-read the reference code.

Consulting AthenaK's src/bvals/physics/z4c_bcs.cpp and Athena++'s src/bvals/bvals_refine.cpp showed that our approach — quadratic extrapolation on the coarse buffer's domain-boundary ghost cells, applied face-by-face in a dimension sweep — was correct. AthenaK's BCHelper does exactly the same thing. The approach was right; the implementation detail was wrong.

Finding the Error Location

Adding debug prints to the ghost-accuracy checker pinpointed the worst error. The maximum error occurred at:

bid=12, (i,j,k) = (4, 4, 21)
boundary flags: nblevel = [1, 0, 1, 0, 0, 0]
  x-: domain boundary (nblevel < 0)
  y-: domain boundary (nblevel < 0)
  z+: coarser neighbor (nblevel = 0, block level = 1)
Cell is in the z+ ghost zone (k=21 >= ghost+N=20)
  at x-ghost position (i=4 = ghost) and y-ghost position (j=4 = ghost)

This cell sits at the intersection of two domain-boundary faces (x- and y-) and one coarse-neighbor face (z+). It is a triple-boundary corner in the coarse_buf — exactly the kind of cell that requires careful coordination between Phase 3 (neighbor copy) and Phase 3.5 (boundary extrapolation).

Root Cause: The Unfilled Corner

The bug is a coverage gap between Phase 3 and Phase 3.5. Neither phase fills cells at the intersection of a domain-boundary ghost zone and a non-boundary ghost zone.

What Phase 3 fills (and misses)

When copy_from_coarse_grid() fills the z+ ghost slab from a coarser neighbor, it computes loop ranges using ghost_range():

ghost_range(ox=0, ...)  // x: not a ghost direction -> interior range [ghost, ghost+N)
ghost_range(oy=0, ...)  // y: not a ghost direction -> interior range [ghost, ghost+N)
ghost_range(oz=+1, ...) // z: ghost direction       -> ghost range [ghost+N, Ntotal)

The z+ ghost slab is filled only for x in [ghost, ghost+N) and y in [ghost, ghost+N). Cells at x-ghost positions [0, ghost) within the z+ slab are not touched.

What Phase 3.5 fills (and misses)

Phase 3.5 processes domain-boundary faces only. It fills x- ghost cells and y- ghost cells, but not z+ ghost cells (z+ has a coarser neighbor, not a domain boundary). The original loop ranges for X-face extrapolation used j in [ghost, ghost+N) and k in [ghost, ghost+N) — interior only. So cells at z-ghost positions within the x- ghost slab were also not filled.

In 3D, a triple-corner cell at (x_ghost, y_ghost, z_ghost+) where x- and y- are domain boundaries and z+ is a coarse neighbor has three unfilled dimensions. The 5-point prolongation stencil reads multiple unfilled cells, producing the observed O(1) error of 0.386.

The AthenaK Pattern: Full-Width Dimension Sweeps

AthenaK's BCHelper (in src/bvals/physics/z4c_bcs.cpp) applies boundary conditions face-by-face with loop ranges that span the full array dimensions [0, Ntotal) in non-ghost directions — not just the interior range [ghost, ghost+N). This is the critical difference.

The sequential ordering (X faces first, then Y, then Z) combined with full-width loops means:

  • The X sweep writes valid data into all x-ghost cells for every j and k, including positions in y-ghost and z-ghost regions.
  • The Y sweep reads x-ghost values that were written by the X sweep, producing correct results at x-ghost/y-ghost intersections.
  • The Z sweep reads both x-ghost and y-ghost values from earlier sweeps.

Edge and corner ghost cells are filled transitively through the sweep chain without any explicit edge or corner handling code.

The Sweep Chain: How Corners Get Filled

Consider a triple-boundary corner cell at (i_ghost, j_ghost, k_ghost) where all three faces are domain boundaries. With full-width loops, the sweep chain fills it through a dependency cascade:

Diagram 2: X, Y, Z sweep chain for a triple-boundary corner

How sequential sweeps fill corner cell (i_ghost, j_ghost, k_ghost): Step 1 — X sweep writes (i_ghost, j_int, k_int) reads interior data at (i_int, j_int, k_int) Source: Phase 2 restriction (always valid) Step 2 — Y sweep writes (i_ghost, j_ghost, k_int) reads (i_ghost, j_int, k_int) ← written by X sweep in Step 1 Source: X sweep output (valid) Step 3 — Z sweep writes (i_ghost, j_ghost, k_ghost) reads (i_ghost, j_ghost, k_int) ← written by Y sweep in Step 2 Source: Y sweep output (valid) Each sweep's output feeds the next sweep's input. The chain terminates at interior data from Phase 2. No cell is left unfilled.

This pattern works for any combination of boundary types at a corner: domain boundaries, coarse neighbors, or same-level neighbors. The key requirement is that the non-ghost loop ranges must span [0, Ntotal) so that ghost-zone positions from earlier sweeps are included.

The 4-Line Fix

The fix widens Phase 3.5's loop ranges in non-ghost directions from [ghost, ghost+N) to [0, Ntotal). Only the X-face and Y-face loops needed changes; the Z-face loops already used full-width ranges.

--- a/src/amr/ghost_exchange.c (buggy: interior-only ranges) +++ b/src/amr/ghost_exchange.c (fixed: full-width ranges) /* X-faces: extrapolate in i */ if (b->nblevel[1][1][0] < 0) { /* x- boundary */ - for (int k = ghost; k < ghost + N; k++) { - for (int j = ghost; j < ghost + N; j++) { + for (int k = 0; k < Nt; k++) { + for (int j = 0; j < Nt; j++) { for (int d = 0; d < gh; d++) { ... } /* Y-faces: extrapolate in j */ if (b->nblevel[1][0][1] < 0) { /* y- boundary */ - for (int k = ghost; k < ghost + N; k++) { - for (int i = ghost; i < ghost + N; i++) { + for (int k = 0; k < Nt; k++) { + for (int i = 0; i < Nt; i++) { for (int d = 0; d < gh; d++) { ... } /* Same fix applied to x+ and y+ boundary faces (symmetric) */

The Z-face loops already iterated over i in [0, Nt) and j in [0, Nt), so they required no changes. After the fix, all six face loops use full-width ranges in their non-ghost directions.

Result

Test 6: max_err dropped from 0.386 to 4.1e-6 (threshold 9.8e-5). That is a 94,000x improvement from a 4-line change. All 72 AMR tests pass. All other test suites unchanged.

Lessons Learned

Lesson 1: O(1) errors mean data is not being written, not computed wrong

An error of 0.386 on data that should be ~1.0 is not a precision problem. It means the cell is reading uninitialized or stale memory. When you see O(1) errors in a simulation that should have O(h^4) accuracy, stop looking at stencil coefficients and start looking at which cells are never touched.

Lesson 2: Changing the coefficients was a red herring

The first instinct was to blame the extrapolation formula. But swapping quadratic extrapolation for flat copy produced the same error — because the unfilled cells were never reached by any extrapolation at all. The lesson: when debugging, test whether the location of the bug matches your hypothesis before changing formulas.

Lesson 3: Dimension sweeps require full-width loops to fill edges and corners

This is a general principle for any dimension-by-dimension algorithm (boundary conditions, diffusion sweeps, ADI methods). If the non-swept dimensions use interior-only ranges, cells at the intersection of ghost zones in multiple dimensions will be missed. The sequential sweep order (X, Y, Z) with full-width loops is the standard pattern that avoids explicit edge and corner handling.

Lesson 4: Read the reference implementation line-by-line, not just conceptually

We knew AthenaK used a dimension sweep for boundary conditions on the coarse buffer. The conceptual understanding was correct. But the implementation used interior-only ranges in the non-ghost directions, which differs from AthenaK's use of n1, n2, n3 (full array dimensions). The difference was not in the algorithm but in the loop bounds — something only visible by reading the reference code line-by-line.

Lesson 5: Debug prints that show cell coordinates and boundary flags are invaluable

The breakthrough came from adding prints that showed not just the error magnitude but the cell indices, block ID, and boundary flags (nblevel) at the worst-error location. The boundary flags [1,0,1,0,0,0] immediately pointed to the boundary/ghost intersection pattern. Without that context, we would have continued guessing at coefficient problems.

Debugging Methodology

The approach that worked here generalizes to any numerical simulation bug. The five steps form a systematic narrowing process:

Step 1: Classify the error magnitude

O(1) = missing data. O(h^n) with wrong n = stencil bug. O(h^n) with right n but wrong prefactor = physics error. This immediately narrows the search space.

Step 2: Locate the worst error

Add debug output that prints block ID, cell indices, boundary flags, and the expected vs. actual values at the maximum-error cell. The position of the error tells you more than its magnitude.

Step 3: Identify what should fill that cell

Walk the pipeline phase by phase and determine which phase is responsible for filling the error cell. If the answer is "none of them," you have found a coverage gap.

Step 4: Cross-reference with the reference implementation

Read the corresponding code in the reference (AthenaK, GRChombo, etc.) line by line. Focus on loop bounds, index ranges, and sweep ordering. Conceptual understanding is necessary but not sufficient.

Step 5: Apply the minimal fix and verify

Change only the identified loop bounds. If the error drops by orders of magnitude, the diagnosis was correct. If it does not change, return to Step 2 with new debug prints.
