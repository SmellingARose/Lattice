Key context: The solver converges on CPU at lower AMR levels (2–5 levels). All unit tests pass at small scale (2–3 levels). The divergence is specific to the GPU path at high level counts.

Bug #1 (Critical): MAX_SOLVER_SLOTS Overflow

ROOT CAUSE — GPU solver slots limited to 8, but 11 AMR levels requested

Levels 8–10 are complete no-ops on GPU. The solver never initializes, smooths, restricts, or prolongates data at the finest 3 levels. All 3 independent audit agents confirmed this as the primary cause.

Location

// src/backend/backend.h:363
#define MAX_SOLVER_SLOTS 8  /* one per AMR level */

// src/backend/backend_hip.cpp:2449
static hip_solver_ptrs_t d_solver[MAX_SOLVER_SLOTS];

// src/initial_data/relaxation_amr.c:1759 — slot = level index directly
levels[L].slot = L;  // L=8,9,10 exceed array bounds

Mechanism

The GPU solver in gpu_build_level_packs() maps AMR level L directly to device solver slot L: levels[L].slot = L. With 11 AMR levels (0–10), it attempts to use slots 0–10.

For levels 8, 9, 10:

  1. backend_map_solver_pack(pack, slot) prints "slot %d out of range" to stderr and returns early — the slot is never initialized (valid = 0).
  2. Every subsequent GPU operation checks !d_solver[slot].valid and returns silently as a no-op:
    • backend_mg_smooth_packed — no smoothing
    • backend_mg_operator_packed — no operator evaluation
    • backend_mg_ghost_full_packed — no ghost exchange
    • backend_mg_restrict_packed — no restriction
    • backend_mg_prolong_add_packed — no prolongation
    • backend_mg_prolong_fmg_packed — no FMG prolongation
  3. backend_mg_l2_norm_packed returns 0.0 for invalid slots.

Consequence

The V-cycle recurses through levels 10 → 9 → 8 doing nothing, then levels 7 → 0 work correctly. The fine levels (where the solution matters most — near the punctures with dx=0.047–0.188) are never solved. The FMG prolongation from level 7 to level 8 is also a no-op, so levels 8–10 contain uninitialized/zero correction data.

The residual computation at the finest level sees unsolved data (zero correction + BL background), which is far from the true solution. The V-cycle cannot fix this because the fine-level operations are all no-ops. The reported residual blows up because the CPU-side residual norm (called after GPU operations) sees the unsolved fine data.

Why tests pass

All tests use ≤ 5 AMR levels, well within the 8-slot limit. The bug only triggers at ≥ 9 AMR levels.

Proposed Fix

// backend.h — change:
#define MAX_SOLVER_SLOTS 8
// to:
#define MAX_SOLVER_SLOTS MAX_AMR_LEVELS  // = 16, defined in mesh.h

One-line fix. This alone should make the 11-level run work on GPU.

Bug #2 (High): Coarse-Data Stride Mismatch in Solver Ghost Exchange

GPU ghost exchange kernels index coarse_data with wrong field stride

The solver ghost exchange reuses evolution ghost kernels but passes n_sol (1 or 4) as the field count, while the coarse_data buffer was allocated with stride MG_AMR_N_FIELDS = 10.

Location

// backend_hip.cpp — backend_mg_ghost_full_packed()
// Passes n_sol (1 or 4) to ghost kernels as "nf" parameter
// But coarse_data was allocated at pack creation with pack->n_fields = 10

// The ghost kernels index as: r * nf * cnpts + f * cnpts
// With nf = 4: block r=1 field 0 is at offset 4*cnpts
// But actual stride in allocation is 10*cnpts — MISMATCH

Mechanism

The ghost exchange kernels (hip_ghost_restrict, hip_ghost_extrap, hip_ghost_prolong, hip_mg_ghost_cf_fill) index coarse_data as r * nf * cnpts + f * cnpts. When called from the solver with nf = n_sol = 4, block r=1 field 0 lands at offset 4*cnpts. But the actual data for that block starts at offset 10*cnpts (since the allocation uses MG_AMR_N_FIELDS = 10). This reads/writes the wrong memory, corrupting ghost zone data at every coarse-fine interface.

Consequence

Incorrect ghost zone values in the FD stencils near refinement boundaries. The error compounds with level count — at 11 levels there are 10 coarse-fine interfaces, each contributing corrupted ghost data to the smoother and operator evaluation.

This bug affects all GPU AMR solver runs, but its impact is small at low level counts where there are few refined blocks and the corrections are small.

Proposed Fix

Pass the actual coarse_data field count (sp->n_fields or pack->n_fields) instead of n_sol to the ghost exchange kernels when indexing coarse_data. Alternatively, allocate coarse_data with n_sol fields and use n_sol consistently.

Bug #3 (Medium): 6th-Order Stencils in 8-Color Gauss-Seidel Smoother

8-color (stride-2) ordering is incompatible with 6th-order (radius-3) stencils under OpenMP

Same-color points at distance 2 share stencil dependencies, creating data races when OpenMP parallelizes the sweep.

Affected Functions

FunctionFileOMP Parallel?

All call fd_d2() which is a 7-point stencil (radius 3) when FD_ORDER=6. The 4-field variants additionally call fd_d2_mixed() which accesses a full 7×7 cross-stencil.

The Race Condition

// 8-color loop structure (stride 2 in each dim):
for (int color = 0; color < 8; color++) {
    int c0 = color & 1, c1 = (color >> 1) & 1, c2 = (color >> 2) & 1;
    #pragma omp parallel for schedule(static)
    for (int k = gw + c2; k < gw + N; k += 2)
        for (int j = gw + c1; j < gw + N; j += 2)
            for (int i = gw + c0; i < gw + N; i += 2)
                // fd_d2(psi, idx, sx=1, inv_dx) reads psi[idx-3] to psi[idx+3]
                // Point i and point i+2 are SAME COLOR but i+2 is IN THE STENCIL of i

For 8-color ordering to be safe, the stencil radius must be ≤ 1 (2nd-order, 3-point). A 6th-order stencil (radius 3) requires stride ≥ 7 in each dimension.

Why it works at small scale

  • The uniform-grid solver (relaxation.c) runs the smoother serially (no OMP pragma). The stencil overlap makes it a “Gauss-Seidel with leakage” that converges deterministically.
  • At low AMR levels with OMP, the corrections are small and the race impact is bounded.
  • At 11 levels with many blocks and full OMP parallelization, the races become severe.

GPU smoother note

The GPU smoother kernel also uses 8-color ordering. GPU threads within a warp execute in lockstep, so same-color points in the same warp do have stencil interference. However, the GPU's execution model (warps of 32 threads) makes the interference pattern different from CPU OMP. On GPU, the primary solver issue is Bug #1 (MAX_SOLVER_SLOTS), not the stencil race.

Proposed Fix (Defect Correction)

The standard approach (HPGMG, AMReX, Dendro, arXiv:2510.11152):

  1. Smoother: Use 2nd-order Laplacian (3-point, radius 1). Compatible with 8-color ordering. The smoother only needs to damp high-frequency error, not be high-order accurate.
  2. Residual/operator: Keep the full 6th-order stencil. The residual computation reads from a frozen solution (no in-place updates), so there is no race.
  3. Jacobian diagonal: Update FD_D2_CENTER_WEIGHT in the smoother to -2.0 (2nd-order center weight) instead of -49/18.
